# AR5 + 因时手 数据采集

遥操已经调通（见 `遥操作_servoJ.md`）。这份是**在遥操上面采数据**：怎么录、怎么检查、
怎么删、怎么转成数据集。

一条 episode = 一个 `.npz` + 每路相机一个 `.mp4`。数据是 13 维：AR5 七个关节角（弧度）
加因时手六根手指（0~1000，0 是握紧）。动作空间是**绝对关节角**，不是增量。

```
1 激活环境  →  2 检查相机  →  3 采集  →  4 回放 + 自动检查  →  5 删和重排  →  6 转数据集
```

---

## 2. 检查相机

每次开工先看一眼。相机没插好、镜头转了、画面冻了，这些在数据里都是安静的。

```bash
python view_cameras.py            # 两路并排实时看
python view_cameras.py --check    # 没有显示器时用：抓 90 帧出体检报告
python view_cameras.py --list     # 只列设备路径
```

窗口里 `q` 退出、`g` 叠网格摆正相机、`s` 存图、`1`/`2` 单看一路。

**要确认三件事**：两路画面都出得来；桌面和物体都在画面里；两路各是什么视角。

现在这台机器上：

| 键名 | USB 口 | 视角 |
|---|---|---|
| `cam_high` | `10.4` | 俯视，正对贴黄胶带的工作区 |
| `cam_front` | `10.3` | 侧视，从台架上看整条臂和手 |

**两路都固定在台架上，没有一路在腕上。** 名字叫 `cam_front` 不叫 `cam_wrist` 就是这个
原因。真把相机装到腕上之后，改 `config.py` 里的键名，不要只改物理位置。

设备路径一律用 `/dev/v4l/by-path/...`，不要用 `video0` / `video2`。两台相机型号和序列号
都一样（都报 SN0001），`by-id` 只剩一条，`videoN` 拔插一次就会互换，结果是俯视画面被喂成
侧视画面，这一批数据全废。`by-path` 绑的是物理插口。

相机跑不到 30 Hz 的两个原因（两个都已经在代码里处理了，这里写出来是为了将来查）：

* `exposure_dynamic_framerate` 这个开关开着，相机会拿帧率换曝光，室内光照下只给 19 Hz，
  改曝光时间、换像素格式都救不回来。开录前会自动关掉它。
* OpenCV 的 `CAP_PROP_BUFFERSIZE` 设成 1 会**正好减半**：实测 15.5 Hz 对 29.3 Hz。
  取图和还缓冲之间驱动没地方放下一帧，于是每隔一帧丢一帧。现在设的是 2。

两项都改好之后实测两路各 29.6 Hz。

## 3. 采集

```bash
python avp_servoj_teleop.py <头显IP> --planner spline --lag-ms 50 \
    --record --task "pick up the bolt and put it in the box" \
    --num-episodes 50 --frame-cap 900 --reset-seconds 5
```

头显 IP 从 Tracking Streamer 界面上读，每次可能变。

### 键盘

| 键 | 做什么 |
|---|---|
| **回车** | 挂 / 摘离合。挂上之后**右手保持捏合**臂才动，松开即停 |
| **空格** | 开始录这一条 |
| **s** | 存盘，**标成功** |
| **←** | 存盘，**不标成功**（不删，只是不当作成功样本） |
| **退格** | 丢弃这一条，编号不变，重录 |
| **h** | 停下并让臂回位 |
| **q** | 退出 |

成功与否写进 npz 的 `success` 字段，训练时按它筛，不用靠人记。按 ← 保留下来的条目
仍然是有效数据 —— 失败轨迹对某些训练方法有用，而且当场判不准的时候留着比删了强。

**存完不会自动开下一条。** 这是故意的：自动往下开的话，每条的头几秒都是你在摆现场，
数据看着正常但前面是空的。`--reset-seconds` 在存盘后挡住空格若干秒，防止手快。

### 关键参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--task` | 空 | 这批数据在做什么，一句英文小写祈使句。**一批之内不要改**，改了不同 episode 的语言条件就不一致 |
| `--num-episodes` | 0（不限） | 采够多少条自动收工 |
| `--frame-cap` | 0（不限） | 一条最多多少帧，到了自动存盘。**按帧数不按秒**：回路周期抖一下不该改变一条的长短。30 Hz 下 900 帧 = 30 秒 |
| `--reset-seconds` | 5 | 存完一条之后空格不响应的秒数 |
| `--record-hz` | 30 | 录制帧率。相机就是 30 fps，设高了只会录到重复帧 |
| `--out-dir` | `~/atom_episodes` | 存哪。**一个任务一个目录** |
| `--cam-top` / `--cam-front` | 用 config 里的 | 只在相机换了 USB 口时才需要给 |
| `--auto-record` | 关 | 接合即开录。**别用**，理由见上 |

编号从目录里已有的最大值往后接，不会覆盖。

### 采的时候注意

* **每条都要换位置。** 物体摆在同一个点采 100 条，训出来的策略只会走那一条轨迹。
  自动检查第 10 项会量起始末端位置的离散度。
* **手要真的张合。** 全程握着不动的话，手那六维学不到东西，自动检查第 9 项会报出来。
* **一条别太长。** 30 秒够做一次抓放。太长的条目里大半是空转。
* **开始录之前先把手放到起始位置**，不要按了空格再去找物体。

## 4. 回放和自动检查

### 自动检查

```bash
python qc_episodes.py --src ~/atom_episodes
```

查十项，逐项打印数字，最后列出要处理的问题：

| # | 查什么 | 判据 |
|---|---|---|
| 1 | 丢帧 | npz 帧数和每路 mp4 帧数一致 |
| 2 | 重复帧 | 相邻两帧逐像素完全相同 = 同一张图被读了两次 |
| 3 | 画面丢失 | 黑帧、低对比帧 |
| 4 | 帧率 | 实测对标称，逐帧间隔的 p50 / p99 / 最大 |
| 5 | 卡顿 | 连续 5 帧几乎不变 |
| 6 | 相机漂移 | 首帧相对静态背景的位移，超过 8 px 报警 |
| 7 | 人手误入 | 肤色占比。**这条不可靠**，木桌和黄胶带都会撞色 |
| 8 | 有效动作 | 开头空转 / 结尾空转 / 中间停顿各占多少 |
| 9 | 手的行程 | 每条内部张合够不够、有没有真正合拢过 |
| 10 | 场景多样性 | 起始末端位置的标准差和跨度 |

第 6 项只在**跨 episode 不变的像素**上量。整帧比对会被臂的起始位置和物体的摆位带偏 ——
以前实测过一条整帧报 73 px、其实相机根本没动。静态区不写死坐标，从所有首帧的逐像素
标准差里自己算，换机位也不用改代码。

第 9 项**不要拿「有没有用满 0~1000」当判据**。任务用不到量程顶部不是缺陷，归一化会自己
适配。要查的是每条内部的行程、有没有合拢到底、有没有哪条手全程没动。

**有两件它查不出来，只能用眼睛看**：人手有没有入镜，以及操作对不对（抓稳没有、放进去
没有）。后者没有自动判据。

### 回放

```bash
python replay_episode.py                        # 列出全部，一行一条
python replay_episode.py --episode 7            # 看第 7 条
python replay_episode.py --all                  # 从头一条条看
python replay_episode.py --all --only-flagged   # 只看列表里带 ⚠ 的
python replay_episode.py --episode 7 --cam cam_front   # 只看侧视那一路
```

`--episode` 给的是**文件名里的编号**，不是列表下标。删过数据之后两者会对不上，
所以按编号找不到时会把现有编号列出来。

窗口里：空格暂停、`←` `→` 单帧步进、`a` `d` 上一条下一条、`q` 退出。
底部六条绿色是六根手指，顶部一行是这一帧末端走了多少毫米。

## 5. 删数据、编号、文件名

```bash
python manage_episodes.py                       # 列出现状：编号、空洞、孤儿文件
python manage_episodes.py --delete 3,7,12       # 先预览
python manage_episodes.py --delete 3,7,12 --apply
python manage_episodes.py --clean-orphans --apply
python manage_episodes.py --renumber --apply    # 补空洞（一批彻底做完再用）
```

**用这个删，不要手动 `rm`。** 一条 episode 是一个 npz 加两个 mp4，手动删最容易只删掉
npz，留下的 mp4 会让后面的检查和转换对不上。`--clean-orphans` 就是收拾这种残局的。

### 编号要不要重排

**采集过程中不要排。** 三条理由：

* 有空洞不影响任何下游。`to_lerobot_dex.py` 按文件名排序读，lerobot 自己重新编
  `episode_index`，空洞会被自动吃掉。
* 重排会让你手上的记录失效。回放时记下「第 12 条抓歪了」，一重排 12 号就是另一条了。
* 重排是批量改名，中途断掉就是一地半新半旧的文件名。

要排就等这一批采完、检查完、转完数据集之后再排一次。`--renumber` 默认只预览，带
`--apply` 才动，并且分两步改名（先全部改成临时名再落位），避免 `1 -> 0` 这种撞车。
映射表写进 `renumber_log.txt`，回放笔记按它对一遍。

### 文件名要不要改

**不用改。** 现在的 `episode_%04d.npz` + `episode_%04d_<相机名>.mp4` 已经够用：编号定位、
相机名在后缀。任务描述、成功标记、时间戳、实测帧率都在 npz 里，`manage_episodes.py`
不带参数就能列出来。把任务名或日期塞进文件名，删改和重排都会变麻烦，而且换任务时
旧脚本的通配符会失效。

**一个任务一个 `--out-dir`**，这比在文件名里区分任务干净得多。

## 6. 转成数据集

```bash
conda activate lerobot
python to_lerobot_dex.py --src ~/atom_episodes --repo-id atom_ar5_bolt
```

时间戳用 npz 里的 `fps_measured`，不是标称的 30 —— 回路实际跑多快事后只能靠它。

## 附：npz 里有什么

| 字段 | 形状 | 内容 |
|---|---|---|
| `state` | (n, 13) | 实测：7 个关节角（rad）+ 6 个手指（0~1000） |
| `action` | (n, 13) | 指令：同上。servoJ 下发的就是绝对关节角，手也是绝对指令角 |
| `ee_pose` | (n, 6) | 实测末端位姿：位置（m）+ 轴角（rad） |
| `ee_target` | (n, 6) | 指令末端位姿。留着以后换动作空间时重算 |
| `timestamp` | (n,) | 每帧相对第一帧的秒数，实测。**转数据集用它** |
| `success` | 标量 | 按 s 存的是 True，按 ← 存的是 False |
| `task` / `fps` / `fps_measured` / `camera_keys` | | |

写盘在后台线程上。servoJ 要求每 8 ms 收到一个关节角，主循环停 2 秒就会被控制器判成
通信丢包，而两路相机 600 帧写一次实测要 2 秒出头。

## 附：以前踩过的坑

* **相机路径用 `videoN`** —— 两台同型号同序列号相机拔插后互换，视角对调，数据全废。
  一律 `by-path`。
* **一条的长度按秒切** —— 回路周期一抖，同样是 30 秒的两条帧数差一截。按帧数切。
* **存完自动开下一条** —— 每条开头几秒都是操作员在摆现场。存完停下，人按空格再开。
* **拿「夹爪用没用满量程」当判据** —— 误报。任务用不到量程顶部不是缺陷。
* **整帧比对量相机漂移** —— 被臂的起始位置带偏，报 73 px 实际没动。只在静态像素上量。
* **肤色检测判人手误入** —— 和木桌、黄胶带撞色，报出来的基本都是误报。只能回放确认。
* **手动 `rm` 删数据** —— 留下孤儿 mp4，后面的检查和转换对不上。
* **一批采到一半改 `--task` 或 `--record-hz`** —— 不同 episode 的尺度和语言条件不一致。
