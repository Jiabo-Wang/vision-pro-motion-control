# 实测数据汇总

这一页把散在各处的真机实测数字收在一起。**全部来自 AR5-5_0.8L-W4C5C11 实机**，
不是仿真、不是厂家标称值。每一项都注明了测法，方便复现或推翻。

---

## 1. SDK 调用耗时

静止态，Python 绑定，本机 → 控制器走以太网。

| 调用 | 耗时 | 备注 |
|---|---|---|
| `moveAppend`（1 条） | **0.03 ms** | 比一次以太网往返还快 → **没等控制器确认**，纯入队 |
| `moveAppend`（20 条批量） | 0.44 ms | |
| `moveStart` | **42.78 ms** | 真往返。**返回时臂还没动** |
| `moveStart` → 首次运动 | **127 ms** | 从调用到臂真的开始移动 |
| `cartPosture(flangeInBase)` | 0.177 ms | 每帧查得起 |
| `operationState` | **0.093 ms**（p95 0.54ms） | 每帧查得起 |
| `queryEventInfo(moveExecution)` | 0.002 ms | 但返回的 `wayPointIndex` 没用（见下） |
| `model().calcIk()` | **41 ms** | RPC，不是本地计算 |
| `checkPath` | **42 ms** | 而且**持 GIL** |

> **一个曾经致命的混淆**：我一度以为 `moveAppend` 要 42ms（那其实是 `checkPath` 的数），
> 据此把整条排队式路径提前判死。实际 `moveAppend` 只要 0.03ms，排队式完全撑得住遥操。

## 2. Python 绑定不释放 GIL

`try_async_start.py` 的 L1：两个线程同时调 `cartPosture`，跑 5 秒。

```
工作线程   26503 次读取
主线程         1 次读取      ← 整整 5 秒只抢到一次
```

**绑定在整个 C++ 调用期间攥着 GIL。** 直接后果：

- 把 `moveStart` 扔到工作线程想给主循环解阻塞 —— **完全无效**：

  | | update() 中位 | p95 | 最大 | 延迟中位 | 延迟 p95 | 位移 |
  |---|---|---|---|---|---|---|
  | 同步 | 1.14ms | 43.20ms | 87ms | 41ms | 92ms | 39.6mm |
  | 异步（工作线程） | 1.18ms | 43.81ms | 87ms | 42ms | 90ms | 40.0mm |

- 反过来也成立：**任何后台线程做 SDK 调用都会饿死遥操主循环**。

## 3. RT 笛卡尔模式：收指令但不动

`try_cartesian_rt.py`。全程 `startMove(cartesianPosition)` 不报错、`sendCommand`
1887 帧零异常。

| 发送方式 | 指令 | 实到 |
|---|---|---|
| trans/rpy, 200Hz | 5mm | 0.00mm |
| trans/rpy, 1kHz, 带 elbow+confData | 5mm | 0.00mm |
| pos16（齐次矩阵）, 1kHz, 带 elbow+confData | 5mm | 0.40mm |
| trans/rpy + pos16, 1kHz, 带 elbow+confData | **20mm** | **0.40mm** |

**最后一行是判据**：指令翻 4 倍、实到不变 → 那 0.4mm 是固定沉降，不是跟踪。

`diag_cartesian_rt.py` 进一步定位：订阅 `pos_c`（指令末端位姿）发现它**从不更新**
—— 指令根本没进控制器的规划器，不是「逆解失败」。

> **被否掉的假设**：以为是缺 `elbow`/`confData`/`hasElbow` 导致 7 轴冗余解不出来。
> 填上了照样不动。

## 4. `moveStart` 的返回码

`diag_movel_state.py` 的 Q2/Q3 逐个问出来的。

| ec | 含义 | 真失败？ |
|---|---|---|
| 0 | 操作成功完成 | — |
| **−20** | 机器人运动中 | **否**。Q3 实测：运动中 append 的点会被**自动接上执行**（指令 6mm 实到 6.0mm） |
| **768** | 没有可执行的运动指令（队列已空） | **否**。没东西要跑 |

> 我一度把 −20 当成「点会搁浅」，改成保留欠账、空闲时补发 —— 结果在队列已空时空放，
> 14 秒报 **28 次假「失败」**。

## 5. `operationState` 可靠性

`diag_movel_state.py` 的 Q1。一段 6mm 的 MoveL：

```
状态进 moving     0 ms
位置停稳        270 ms
状态退 moving   357 ms       → 状态比位置晚 +87ms
状态序列        moving → idle
实到            6.00 mm
```

**方向是对的**：它绝不会在臂还在动的时候说 idle，只会晚一点说。

用位置判（连续 N 帧不动，≈60ms）则**太急** —— 臂物理上停了但状态还没退，
`moveStart` 被拒 `ec=-20`，14 秒里失败 14~20 次。换成 `operationState` 后 **0 次**。

## 6. MoveL 后端：速度与死区

走走停停（动 1.2s 停 0.8s，模拟真实遥操），±20mm 正弦 0.4Hz。

### 6a. 干净目标（无噪声）—— 偏乐观

| `--movel-speed` | 延迟中位 | 跳帧率 |
|---|---|---|
| 150 mm/s | 66ms | 52% |
| 250 mm/s | 41ms | 30% |
| 400 mm/s | 41ms | 21%（现场反馈「太快了」） |

### 6b. 带 0.82mm 残余手抖（真实情况），速度固定 250mm/s

| `--movel-deadband` | 延迟中位 | p95 | 跟踪 RMS | 总位移 |
|---|---|---|---|---|
| 0.5 mm | 73ms | 114ms | 19.7mm | 39.2mm |
| 1.5 mm | 61ms | 133ms | 19.8mm | 39.7mm |
| **3.0 mm** | **37ms** | **93ms** | **14.2mm** | 40.2mm |

**延迟砍掉一半，跟踪精度反而变好。**

### 6c. 死区会不会吃掉精细动作 —— 不会，反而更准

8 秒缓慢走 6mm（0.75mm/s，**比死区本身还慢**）：

| `--movel-deadband` | 实到 | 下发条数 |
|---|---|---|
| 0.5 mm | 3.79mm | 214（臂在追噪声，跟不上） |
| **3.0 mm** | **6.01mm** | 2（精准到位） |

因为死区是对**上一个已下发点**的增量阈值，慢速运动会累积过阈，一个都不丢。

### 6d. 为什么死区这么有效：短段跑不到指令速度

抖动路径上段长约 1mm 时，**臂实测只跑到 25~33 mm/s，而指令是 250 mm/s**
（用相邻采样的最大位移换算：0.5~0.66mm / 20ms）。

峰值速度 ≈ √(加速度 × 段长)。段被抖动切碎 → 每段都在加速阶段就结束了。

### 6e. 一次典型运行的帧账（16 秒）

```
共 597 帧循环（≈37Hz —— sleep(0.02) 加上查状态的开销，不是 50Hz）
 ├─ 440 帧（74%）  目标几乎没动           → 死区拦下
 ├─  93 帧（16%）  臂还欠着债             → 前导闸门拦下
 └─  64 帧（11%）  真动了且臂跟得上       → 下发   = 4 Hz
重启 8   已在动 10   队列空 2   真失败 0   错误 0
```

## 8. AR5 的真实几何（从控制器读出的 DH）

`read_dh.py` → `ar5_dh.json`。确认是标准 **S-R-S** 构型：

| 部位 | 轴（0 基 / 1 基） | 交点 | 误差 |
|---|---|---|---|
| 肩（球） | j0,j1,j2 / **J1,J2,J3** | (0, 0, 0.1745) | **0.23 mm** |
| 肘（单轴） | j3 / **J4** | 10.5mm 偏置 | — |
| 腕（球） | j4,j5,j6 / **J5,J6,J7** | (0, 0, 0.7845) | **0.32 mm** |

推导出的精确关系：

```
R_F2 = Rz(j0)·Ry(j1)·Rz(j2)                       ZYZ，误差 1.1e-16
Rx(-90)·R_wrist·Rx(180) = Rz(j4)·Ry(j5-90°)·Rz(-j6-90°)
|v(j3)|² = A + R·cos(j3 - φ)                      精确，误差 3.3e-16
```

## 9. 解支可达性（反直觉）

理论上 7 轴 S-R-S 有 2³ = 8 个解支。**这台臂实际够不着那么多**：

| 翻转 | 可达率 |
|---|---|
| 肩部翻转 | 99% |
| 肘部翻转 | 58% |
| **腕部翻转** | **0.00%** |

平均 **3.15 个**解支可达，**从来没有 8 个**。腕翻转 0% 是因为 J6/J7 只有 ±50°，
翻 180° 根本转不过去。

### 停手之后的「尾巴」

速度归零 → 截止频率掉到 min_cutoff（1Hz）→ 时间常数 159ms。停手瞬间没走完的距离
要花几百毫秒才爬完 —— 这就是「每段动作结束后臂还小修一下」的主因：

| 手速 | 停手瞬间还差 | 收敛到 1mm | 收敛到 0.2mm |

| 10 cm/s | 6.8 mm | 180 ms | 360 ms |
| 20 cm/s | 10.2 mm | 180 ms | 340 ms |
| 40 cm/s | 14.5 mm | 160 ms | 280 ms |

## 12. 还没测的 / 不确定的

诚实起见单列一节：

- **真头显端到端延迟没测过**。上面 MoveL 的所有数字用的是**合成手抖**
  （σ=0.47mm/轴，按 One-Euro 残余 0.82mm 反推）。Tracking Streamer 在整个调试期间
  没能起来（12345 端口一直 ECONNREFUSED）。
- **控制器插补周期 1kHz 是推断，不是实测**。依据是 SDK 要求 `sendCommand` 1ms 一帧。
- **TCP 和负载是估的**：`--tcp-z` 按 211.5mm 的 70% 猜，负载强制 0
  （官方 790g 与实测外力 ~1.41kg 对不上）。不影响位置跟踪，做接触任务前要实测。
- **掌法向的符号没在真机上验过**。
- **触觉寄存器（3000+）读出来的值超出文档量程**，疑似字节错位。
- **`elbow` 字段的角度约定**（零位在哪、正方向）厂家文档里没查到。我们是原样读、
  原样传，没依赖它的数值含义。
