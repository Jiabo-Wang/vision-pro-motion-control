## 问 1

> 测试了，有个问题，手臂的左右前后和我实际的手是相反方向，其次手的精确度有问题，我左手捏合了但是机器手没捏合而且距离很远，但是握拳没问题，是不是要做mapping


两个问题性质不同，分开解。先查一件跟第二个问题直接相关的事 —— 现有配置里两指捏取到底是命令到哪个值。

查到关键数据。现有**已验证**的两指捏取命令值是：

| | 命令值 | 注释 |
|---|---|---|
| `finger_close`（食指） | **480** | 接触点 495 再进 15 |
| `thumb_close`（拇指弯曲） | **500** | 拇指 500 时食指接触点约 490 |

**我的钳位（食指 ≥520）比这更保守，等于永远够不到接触点 —— 捏不住东西是必然的。** 那个 520/320 是我自己推的，不如直接用他们实测验证过的值。

两个问题分别解决：

现在解决捏合。**根因**：人捏合时食指只是中等弯曲（主要在掌指关节），拇指几乎不弯 —— 是**对掌**把指尖带到一起的。所以"弯曲角之和"这个量说"才半闭"，而实际指尖已经碰上了。

加一路**指尖距离**驱动，和弯曲量取"更闭合者胜"。

Now 把捏合姿态加进标定流程。

捏合映射生效了。但我注意到一个**陈旧配置的坑**：输出下限是 520/320 而不是新的 480 —— 因为 `Calibration.load` 会从标定文件里读 `limits`，你那份文件里存的是旧值。加个提示，别让它静默生效。

两个来源的钳位不一致会让人搞不清哪个生效。让驱动层取**两者的交集**（更严者胜）—— 这样陈旧的标定文件只可能把安全带收紧，绝不会放宽。

交集生效了：`index:520-1000`（取标定文件里更严的）、`thumb_bend:480-1000`（取代码里更严的）—— 两边各让一步，永远是严的那个赢。

两个问题性质不同，分别说。

## 1. 臂方向反了 → 加 `--yaw 180`

**左右和前后同时反相 = 绕 Z 转 180°**，这正是 `--yaw` 存在的理由，不用改代码：

```bash
python avp_arm_teleop.py 192.168.0.4 --yaw 180 --no-cameras
```

原因：头显的「前」是 App 启动时你面朝的方向。你面对机器人站着，你的"前"就是臂基座的"后"，两个水平轴一起翻。

（如果只有**单个**轴反相，那是镜像，`--yaw` 修不了 —— 但你说的是左右前后都反，正好是 180°。）

## 2. 捏合捏不住 —— 是我那个特征本身的盲区

**根因**：我用的是「每根手指各节之间的弯曲角之和」。

- **握拳**：每一节都真的弯到底 → 弯曲量很大 → 映射正确 ✅
- **捏合**：食指只是中等弯曲（主要弯在掌指关节），**拇指几乎不弯** —— 把两个指尖带到一起的是**对掌**，不是弯曲。所以弯曲量说"才半闭"，机械手就停在离很远的地方 ❌

你描述的「握拳没问题、捏合离得很远」完全符合这个盲区。

**修法**：另算一路**拇指尖到食指尖的距离**，和弯曲量那一路**取更闭合者胜**。握拳时弯曲量赢，捏取时距离赢。

```
指尖距离    食指   拇指弯曲
   9.0cm   1000     1000
   5.0cm    744      637
   3.0cm    616      456
   1.5cm    520      320   ← 接触点附近，靠力控停住
```

## 顺带修正了我自己定的钳位（这个也在挡你）

我原来给的 `index ≥ 520 / thumb ≥ 320` 是自己推的。查了 config.py 才发现，**你们实测验证过的两指闭合命令值是 `finger_close = 480`（注释：接触点 495 再进 15）、`thumb_close = 500`** —— 比我的 520 更闭。

**我的钳位比验证过的值还保守，等于让机械手永远够不到接触点，捏不住是必然的。** 已改成两维都 ≥480，真正的过载保护是力控阈值，不是钳位。

## 你必须重跑标定

两个原因：

1. 标定要多采**第三个姿态**（拇指食指捏在一起），捏合精度全靠它
2. 你现有的 `hand_calib.json` 里存了**旧钳位快照**（520/320），会盖掉新值

不重标的话现在会这样提示你（我加的，不让它静默生效）：

```
⚠ 标定文件里的安全钳位和当前代码不一致（文件里的生效）：
    index       文件 (520, 1000)  代码 (480, 1000)
    thumb_bend  文件 (320, 1000)  代码 (480, 1000)
⚠ 这份标定没有捏合端点，正在用通用兜底 9cm/1.5cm
```

钳位现在取**两个来源的交集**，陈旧文件只可能收紧、不可能放宽。

## 问 2

> 手的 TCP 标定填上怎么做


好问题 —— 这事有两半：**几何（TCP 位置/姿态）**和**动力学（质量/质心）**，方法完全不同。先看 SDK 和驱动里已经有什么。

两个关键确认：

- **TCP 几何**：SDK 有 `calibrateFrame(FrameType.tool, points, is_held=True, ec)` —— N 点标定法（工具支持三点/四点/六点），`points` 是 N 组**关节角**（弧度，7 个一组），返回值还带 `errors = [最小,平均,最大]` 偏差（米），自带质量判据。
- **负载辨识**：SDK **没有**触发接口，只有 `OperationState.loadIdentify` 这个状态枚举。所以要么在示教器里做，要么自己想办法。

先看有没有拖动示教（有的话标定会轻松很多）。

查清楚了，三个数各是什么、怎么得到，方法完全不同。

## 先说这三个数是什么

| 字段 | 含义 | 单位/格式 |
|---|---|---|
| `tcp_offset` | **末端执行器坐标系相对法兰的位姿** | `(x,y,z,rx,ry,rz)`，米 + 轴角弧度 |
| `payload_mass` | 法兰之后挂的总质量 | kg |
| `payload_com` | 质心，**在法兰坐标系里** | `(x,y,z)` 米 |

驱动 [rokae_arm.py:521-532](vel_ar5/openvla-energy/experiments/robot/ar5/drivers/rokae_arm.py#L521-L532) 已经写好了下发逻辑（`setLoad` / `setEndEffectorFrame`），只要配置里填了非零值就会自动应用。**填数就行，不用改代码。**

注意 SDK 说明：`setEndEffectorFrame` 设的 TCP **重启机器人会恢复默认**，所以必须每次连接重设 —— 驱动已经是这么做的。

## TCP 几何：用 SDK 的 N 点标定

```python
result = robot.calibrateFrame(FrameType.tool, points, is_held=True, ec)
#   points  : N 组关节角（弧度，7 个一组）
#   工具坐标系支持 三点/四点/六点法
#   返回 result.frame  和  result.errors = [最小, 平均, 最大] 偏差（米）
```

**`errors` 是自带的质量判据** —— 标完直接告诉你这组点有多自洽，不用自己判断标得好不好。

操作流程：

1. 台面上固定一个**尖的参照点**（针尖、螺丝尖都行）
2. `enableDrag(轴空间, 自由拖拽, ec, True)` 开拖动示教（AR5 是力控臂，支持手拖）
3. 手把**指尖**移到那个参照点上，**换不同姿态**重复 4~6 次 —— 每次都碰同一个物理点，但机器人姿态要差得明显
4. 每次按一下键记录当前 `jointPosition(ec)`
5. 全部记完调 `calibrateFrame`，看 `errors` 的平均值。**几毫米算合格，超过 1cm 就重来**
6. 把 `result.frame` 转成 6 元组写进 `config.tcp_offset`

**省事的替代**：拿卡尺量法兰端面到指尖的距离，直接填 `(0, 0, 0.18, 0, 0, 0)` 之类。精度差些，但比现在全 0 强太多，地板保护立刻就对了。

## 负载：SDK 没有接口，得自己来

我翻遍了 SDK，**只有 `OperationState.loadIdentify` 这个状态枚举，没有任何触发辨识的方法**。所以三条路：

**A. 称重 + 量质心（最快，半小时）**
- 把手连同转接板、线缆一起放秤上 → `payload_mass`
- 质心：手大致是均匀的，取法兰到手几何中心的距离即可，Z 方向填一半长度

**B. 示教器/RobotAssist 里跑官方负载辨识**（最准，但要用示教器）

**C. 用臂自己的力矩传感器反解**（不用示教器，我可以写）

C 的原理：我们已经验证过 `getEndTorque` 是活的。现在 `payload_mass=0`，所以静止时读到的"外部力"**就是手的重力没被补偿掉的部分** —— 上次实测是 `[9.974, -0.084, 9.613] N`（约 13.9N ≈ 1.4kg，比 RH56 标称的 0.5kg 大，因为含转接板和线缆）。

摆若干个**不同姿态**、每个姿态静止读一次外部力和力矩，就能最小二乘解出质量和质心：

```
F_法兰 = -m · R_法兰→基座ᵀ · g
τ_法兰 = c × F_法兰        （c 就是质心）
```

只要 6~8 个姿态就够。**全程只读，臂由你手拖或点动，脚本不发运动指令。**

## 一个先后顺序的坑

**拖动示教依赖动力学模型，而模型里就有负载。** 现在 `payload_mass=0` 但实际挂着 1.4kg，拖动时臂会"往下坠"、手感发飘。

所以顺序应该是：

1. **先称重**，把 mass 填个粗值（哪怕只是 1.4kg 这个估计）→ 拖动手感立刻变正常
2. 再用拖动做 **TCP 标定**
3. 最后用方法 C 精修 mass 和 CoM

## ⚠️ 一个要先试的风险

`solve_ik` 的注释里写着：

> the xMate model library does not support the AR series —— `robot.model()` raises「xMate模型库暂不支持的机型」

**所以 `calibrateFrame` 在 AR5 上也可能不被支持。** 这个要先用一次废数据试探，别等标了 6 个点才发现调不通。

- **`calib_tcp.py`** —— 开拖动、按键记点、调 `calibrateFrame`、打印 `errors`、生成可直接粘进 config 的 6 元组。**会先做一次探测确认 `calibrateFrame` 在 AR5 上可用**，不可用就退回手工量的路子。

## 问 3

> 我现在操作发现左右转动手腕没问题，但是上下挥手做不到


这是我设计的过滤器在起作用 —— 不是故障。

`--rot-mode roll`（我设的默认值）**只保留绕工具接近轴的分量**。工具 Z 朝下时，绕它转 = 转手掌（你感觉是左右转动），而上下挥手是绕一根**垂直于**它的轴，正好被我丢掉了：

```
纯绕工具Z(转手掌)  -> 保留
纯绕base X(翻腕)   -> 丢弃   ← 上下挥手在这里被砍掉了
纯绕base Y(点头)   -> 丢弃
```

当初砍掉是因为你撞了限位。但**那次撞限位的根因是姿态没有缰绳**，而缰绳现在已经加上了 —— roll 只是额外的一层保险。既然你需要上下，就该把这层去掉。

先加个诊断，让你能直接看见哪个轴被砍了多少。

Mock 发的是单位旋转，测不出丢弃量。给它加上手腕旋转再验一次 —— 顺便这个 mock 你以后也能用来离线试参数。

**这不是故障，是我设的过滤器在起作用 —— 而且现在该去掉了。**

## 为什么只有左右能动

`--rot-mode roll`（我设的默认值）只保留**绕工具接近轴**的旋转分量。工具 Z 朝下时，绕它转 = 转手掌（你感觉是左右拧），而上下挥手是绕一根垂直于它的轴，被整个投影掉了。

加了诊断后离线实测，对比很直观：

```
rot-mode=roll   Δrot= 0.3°(丢 0.4°)   Δrot= 0.2°(丢 0.8°)
                累计丢弃姿态 69°        ← 6 秒里丢了这么多

rot-mode=full   Δrot= 0.7°            Δrot= 1.0°
                （没有丢弃行）
```

## 直接用 `--rot-mode full`

当初砍掉两个轴，是因为你撞了限位。但**那次撞限位的根因是姿态指令没有缰绳** —— `AR5Env._leash()` 和 `_base_pose()` 的重锚判据都只看平移，姿态可以无界跑飞。那个根因上一轮已经堵住了，`roll` 只是我额外加的一层保险。

既然你需要上下，就该把这层保险去掉：

```bash
python avp_arm_teleop.py 192.168.0.4 --yaw 180 --with-rotation --rot-mode full --rot-scale 0.5 --no-cameras
```

先用 `--rot-scale 0.5` 跑，稳了再提到 1.0。

## 新增的诊断

状态行现在会显示被丢弃的量：

```
Δrot= 0.3°(丢 0.4°)        ← roll 模式砍掉了多少
Δrot= 1.0°                 ← full 模式，没有丢
[姿态缰绳 22°]              ← 缰绳触发了，指令领先实测太多
```

收尾统计里有 `姿态缰绳触发 N` 和臂的真实拒绝原因：

```
臂 RT: 已发 xxx  迟到 x  限位命中 x  latch=False
臂拒绝的目标: {'limits': 12}
```

## 如果 full 还是超限

按这个顺序调，**别一上来就退回 roll**：

1. **`--rot-scale 0.3`** —— 手转 30°，臂只转 9°，先确认方向对不对
2. **`--max-rot-lead 0.2`**（≈11°）—— 缰绳收紧，臂跟不上时更早停发
3. 看收尾的 `臂拒绝的目标`：
   - `limits` 大 → IK 解不出来，多半是姿态要求超出 7 轴臂从当前构型能达到的范围。换个起始姿态（让臂的腕关节离限位远一点）再试
   - `jump` 大 → 单步跳变太大，降 `--rot-scale`
   - `latched: True` → 撞停了，**按一次 ENTER 就能解锁**，不用重启

顺带把 mock 也升级了（现在会同时做"绕 Z 拧"和"绕 X 上下挥"两种手腕动作），你要离线试参数可以直接用，不占真机。

---

提醒一句上次说过但还没做的事：**`tcp_offset` 还是全 0**，所以旋转是绕**法兰**转的，不是绕手心。手往外还有十几厘米，上下挥的时候指尖会画一个比你预期大得多的弧 —— 这也会让它更容易顶到工作空间边界。TCP 标定那件事值得优先做掉。

## 问 4

> 更不对了，转不动手，你看看你的跟踪程序，我要求左手什么姿态机械手就应该什么姿态


**你说得对，是我的跟踪方式本身就错了。**

我做的是**增量跟踪**：每帧算「这一帧相对上一帧转了多少」，然后把这个增量喂给臂。问题在于 —— 增量一旦被吃掉就**永远找不回来**：

- `max_step_rotation` 每步只放 0.1 rad，超出的部分丢掉
- 姿态缰绳触发时我直接把增量清零
- 被关节限位拒绝的那一步，整个增量作废
- 自救重锚之后，和你手的对应关系彻底断了

于是你的手和机械手之间没有任何固定的对应关系，越积越偏，最后就是"转不动"。

**你要的是绝对姿态映射**：手摆成什么样，末端就该是什么样。那应该是**伺服到目标**，不是累加增量 —— 被吃掉的部分下一帧还会作为剩余误差继续下发，自己会追回来。

我重写跟踪核心。

现在必须验证核心主张：**绝对伺服在被钳位的情况下不丢运动，增量会丢。** 写个闭环仿真直接对比两种做法。

钳位没触发（我给的转速不够快）。而且真实系统里更主要的丢失来源是**被拒绝的那些步**（IK 失败/限位）—— 整帧作废。把这两个都模拟进去。

钳位触发后绝对伺服已经明显更好（平均 17.3° vs 27.8°）。但最关键的性质还没展示出来 —— **误差会不会累积**。做个决定性测试：**快速转一阵，然后手不动**，看末端能不能追上来。

**决定性证据**：手停下后，增量累加的偏差永远停在 34.3°，绝对伺服自己追回到 0.0°。

**你指对了 —— 我的跟踪方式从根上就是错的。**

## 错在哪

我做的是**增量跟踪**：每帧算「这一帧相对上一帧转了多少」，累加给臂。而增量一旦被吃掉就**永远找不回来**：

- `max_step_rotation` 每步只放 0.1 rad，超出部分丢弃
- 姿态缰绳触发时我直接把增量清零
- 被 IK/关节限位拒绝的那一步，整帧作废
- 自救重锚之后，和你手的对应关系彻底断了

所以你的手和末端之间**没有任何固定对应关系**，误差单向累积，越转越偏 —— 就是"转不动手"。

## 仿真实测（前 4 秒手快速乱转超出臂跟随能力 + 15% 丢帧，第 4 秒起手定住不动）

| | 转动中 | 手定住后 5s | 6s | 8s |
|---|---|---|---|---|
| **增量累加** | 27.6° | **34.3°** | **34.3°** | **34.3°** |
| **绝对伺服** | 27.5° | **0.0°** | **0.0°** | **0.0°** |

增量累加：手停了，末端也回不到该在的姿态，**偏差永远挂在那**。
绝对伺服：手一停就自己追回来。

## 改成绝对伺服

**接合瞬间**锁定基准（手的位姿 + 末端的位姿），之后每帧算**绝对目标**，把「目标 − 当前指令」下发：

```
p_target = p_tool0 + A @ (p_hand − p_hand0) × scale
R_target = A @ (R_hand @ R_hand0ᵀ) @ Aᵀ @ R_tool0
delta    = 目标 − 当前指令                    ← 还差多少就发多少
```

被钳位只是**慢一点到位**，剩余误差下一帧继续发。丢一帧也不要紧，下帧照样发全量误差。

接合时会打一行确认：
```
[接合] 已锁定基准，从现在起「手什么姿态，末端就什么姿态」
```

松手即弃基准，重新捏合时就地重锚 —— 手还是可以自由归位。
