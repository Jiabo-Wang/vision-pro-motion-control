## 1. 为什么每段动作结束后臂还会小修一下

**这不是「修正」，是延迟的可见形态。** 你停手的那一刻，管线里还有东西没走完，臂会把它们补完 —— 看起来就像最后又动了一小下。

按贡献从大到小，有三段积压：

### ① One-Euro 滤波的尾巴（两个后端都有，通常是主因）

截止频率跟着速度走：你挥手时 fc 高、滤波轻；**你一停，速度归零，fc 掉到 1Hz**，时间常数 ~159ms。于是停手瞬间没走完的那段距离，要花几百毫秒慢慢爬完。

用当前默认（`--arm-smooth 1.0 --arm-smooth-beta 3.0`）实算：

| 手速 | 停手瞬间还差 | 收敛到 1mm | 收敛到 0.2mm |
|---|---|---|---|
| 10cm/s | 6.8mm | 180ms | 360ms |
| 20cm/s | 10.2mm | 180ms | 340ms |
| 40cm/s | 14.5mm | 160ms | 280ms |
| 60cm/s | 17.6mm | 140ms | 240ms |

**验证方法**：加 `--arm-smooth 0` 跑一次。尾巴应当完全消失（代价是抖动回来）。

### ② movel 特有：队列积压 + 跳帧压着的目标

动起来的时候 30% 的帧被前导闸门跳掉（`lead > 12mm` 就不下发），`_last_target` 被冻在半路。你一停，臂追上来、闸门放开，**最新目标才被补发出去** —— 实测前导 p95 是 93ms × 250mm/s ≈ **23mm**。这段路必须在停手之后走。

### ③ 收尾的最后一步

- **movel**：死区残留 ≤3mm；而且**队列最后一个点不切转弯区**，必须精确到位，所以末尾有一段减速贴靠。
- **rt**：[avp_arm_teleop.py:1472](avp_arm_teleop.py#L1472) 是 `delta = (目标 − 当前) × --gain`，gain=0.5 是指数逼近 —— 10mm 误差经 8 帧(160ms)收到 0.04mm，肉眼就是一小段减速贴近。

### 怎么区分你看到的是哪一种

| 现象 | 是什么 | 怎么压 |
|---|---|---|
| **单向**贴近，越走越慢，几百毫秒收住 | ①②③ 的延迟尾巴 | `--arm-smooth 2.0 --arm-smooth-beta 10`（滞后减半）；`--movel-lead-ms 30` |
| **来回**小幅抽动，不收敛 | movel 死区被残余抖动反复触发：到上一个下发点的距离在 3±0.8mm 之间晃，偶尔越阈就补发一个点 | `--movel-deadband 4.0`（拉开到抖动够不着）或 `--arm-smooth 0.6`（把抖动压小） |

## 2. One-Euro 是什么

一句话：**截止频率会跟着速度变的低通滤波器**。实现在 [avp_arm_teleop.py:227-268](avp_arm_teleop.py#L227-L268)。

它解决的是普通低通的死结：

> 要压住抖，截止频率就得低；截止频率一低，快速运动就跟不上。
> 遥操里表现成「不抖了，但发糊、手停了臂还在飘」。

One-Euro 的做法是让截止频率**自适应**：

```
fc = min_cutoff + beta · |估计速度|
α  = 1 / (1 + τ/Δt)，   τ = 1/(2π·fc)
输出 += α · (输入 − 输出)
```

- 手停住 → 速度≈0 → fc = min_cutoff（1Hz）→ 压得死，抖动没了
- 快速挥动 → 速度大 → fc 升上去 → 几乎不滤，跟手

速度本身也是估出来的、也带噪声，所以**速度先过一层固定截止的低通**（`d_cutoff`），否则抖动会把 fc 顶上去，滤波器自己失效。

两个旋钮：

| 参数 | 管什么 | 往哪调 |
|---|---|---|
| `--arm-smooth` (min_cutoff) | **静止时**压多狠 | 还抖 → 调小(0.6)；停手尾巴长 → 调大(2.0) |
| `--arm-smooth-beta` | **运动时**放多开 | 发糊/跟不上 → 调大(10) |

出处：Casiez, Roussel, Vogel, *1€ Filter*, CHI 2012 —— 原本就是给手势/动捕交互设计的。

## 3. 死区是什么

**幅度阈值**：目标相对**上一个已下发的点**动得比阈值还少，就整帧不发。实现在 [movel_stream.py:236](movel_stream.py#L236)。

关键在「相对上一个**已下发**的点」而不是绝对位置 —— 这决定了它**不丢运动**：

```
你缓慢移动 0.5mm/帧，死区 3mm
帧 1~6   累积 0.5→3.0mm，都不发
帧 6     累积到 3mm，越阈 → 发一个点，_last_target 更新
帧 7~12  再累积 3mm → 再发一个
```

慢速运动只是被**量化**成 3mm 一跳，一点都没少。实测 8 秒缓慢走 6mm（0.75mm/s，比死区本身还慢），死区 3.0mm 实到 **6.01mm**。

### 死区和滤波的区别

这是两个完全不同维度的工具：

| | 作用维度 | 对真实运动 |
|---|---|---|
| 低通滤波 | **频率域** —— 砍高频 | 全频段都拖慢（有滞后） |
| **死区** | **幅度域** —— 砍小幅 | **零滞后**，过阈原样通过 |

手抖是**小幅、宽频**的。用滤波去砍它，必然连带把真实运动也拖慢；用死区砍它，真实运动（幅度大）根本不受影响。这就是为什么这里加死区比加大滤波划算。

代价是位置分辨率被量化到死区大小，以及停手时最多残留一个死区的偏移（就是上面 Q1 那个「来回小抽动」的来源）。

## 4. MoveL 的本质原理

**MoveL = Move Linear**：让**末端在笛卡尔空间走直线**到目标位姿。

### 和兄弟指令的区别

| 指令 | 末端轨迹 | 关节轨迹 | 用途 |
|---|---|---|---|
| MoveJ | 弯的（不可预测） | 各轴同步插值 | 快速转移，不在乎路径 |
| **MoveL** | **直线** | 由逆解决定 | 接近工件、装配、遥操 |
| MoveC | 圆弧 | 同上 | 绕行 |

### 控制器内部做了什么

这是关键 —— 不是「算一次逆解然后发过去」：

```
你发一个目标位姿
      ↓
① 路径生成：起点→终点的直线，姿态用四元数 slerp 插值
      ↓
② 速度规划：在这条线上排一条速度曲线（梯形/S 曲线），
   受 speed / 加速度 / 加加速度 限制
      ↓
③ 每个插补周期（1kHz）：取出这一时刻的笛卡尔位姿 → **做一次逆解** → 关节角
      ↓
④ 关节伺服环执行
```

**逆解是每个插补周期做一次，不是一次。** 这就是为什么把逆解交给控制器会「丝滑不少」—— 我们本地 50Hz 算的逆解，控制器在中间又插了 20 个点。

### 队列语义

```
moveAppend(cmd)   → 塞进 FIFO 缓冲（setMaxCacheSize(300)），0.03ms，不阻塞
moveStart()       → 开始消费队列，42.8ms 往返
```

**提交任务式**：每个点都会被执行完，不会被新指令覆盖。这和 RT `sendCommand` 的**流式覆盖式**（新指令盖掉旧的）是根本区别，也是我们要死区、要前导闸门、要判「队列空没空」的全部原因。

### 转弯区（zone）

相邻两段之间，如果第一段的终点带 zone 半径 r，规划器**不在那个点停下**，而是在半径 r 内把上一段的减速和下一段的加速混在一起，**切个角过去**：

```
zone = 0（fine）:  A ──→ B（停） ──→ C      一段一停，顿挫
zone = 3mm     :  A ──→ ╰B╯ ──→ C         切角，连续
```

所以流式下发时必须给 zone，否则每个点都停一下。**但队列的最后一个点永远是 fine 点**，必须精确到位 —— 这就是 Q1 里「末尾一段减速贴靠」的来源。

### 7 轴的额外一件事

笛卡尔位姿只有 6 维，AR5 有 7 个关节 —— **位姿定不住第 7 个自由度**（肘绕「肩—腕」连线转）。所以 `CartesianPosition` 除了 `trans`/`rpy` 还要带：

- `elbow`：臂角，把肘的位置定死
- `confData`：构型/解支（肩左右、肘上下、腕翻转）
- `setDefaultConfOpt(False)`：取**离当前轴角最近**的解 —— 遥操要的正是这个，分支不会突跳

### 一个反直觉的实测事实

`c.speed = 250` 是**上限，不是实际速度**。段一短，加速度限制就主导了 —— 实测抖动路径上（段长 ~1mm）臂只跑到 **25~33mm/s**，指令是 250。这就是死区效果那么好的真正原因：**它把段拉长，臂才提得起速**。

## 1. 提交任务式 vs 流式覆盖式 ≠ 阻塞 vs 非阻塞

**不对，这是两个正交的维度。**

| | 问的是什么 |
|---|---|
| **阻塞/非阻塞** | **API 调用**会不会等运动做完才返回 |
| **提交任务式/覆盖式** | **还没执行的指令**，在新指令到来时会不会被丢掉 |

我们这套系统里**两条路都是非阻塞的**：

- `moveAppend` 0.03ms 返回，`moveStart` 42.8ms 返回但臂还没动 → 非阻塞 + **提交任务式**
- RT `sendCommand` 立即返回 → 非阻塞 + **覆盖式**

所以区别完全不在阻塞上，在**指令的寿命**：

```
提交任务式：指令是「任务」。队列 [A][B][C]，每个都必须走完。
           会积压 → 延迟会涨 → 所以我要靠「不发」来控延迟（跳帧/死区）

流式覆盖式：指令是「当前期望状态」。新的盖掉旧的，队列深度恒为 1。
           不会积压 → 延迟天然只有一个周期
           但你必须**一直发**：0.25 秒不发，驱动就判定回路死了 → 刹车 latch
```

打个比方：提交任务式是**快递单**（每一单都得送到），覆盖式是**仪表盘读数**（只有最新那个有意义，旧的没人关心）。

## 2. RT 到底是什么

RT = Real-Time，在 xCoreSDK 里是 `MotionControlMode.RtCommandMode`，对面是 `NrtCommandMode`（Non-real-time）。

**本质区别是「谁来做轨迹规划」：**

| | Nrt（MoveL 走这条） | RT |
|---|---|---|
| 你发什么 | 高层指令：「走到这个位姿」 | 原始设定点：这一毫秒该在哪 |
| 谁生成轨迹 | **控制器** | **你** |
| 频率要求 | 随便，你想发就发 | **1ms 一帧**，慢了判通信丢包 |
| API | `moveAppend`/`moveStart` | `getRtMotionController()` → `startMove(模式)` → `sendCommand()` 循环 → `stopMove()` |
| 可用模式 | — | `jointPosition` / `cartesianPosition` / `jointImpedance` / `cartesianImpedance` / `torque` |

我们这套里 RT 路径长这样：

```
我的遥操循环 50Hz  →  本地逆解（旋量法 1.9ms）→ 7 个关节角，写进共享变量
                                                         ↓
驱动的后台发送线程 1kHz（rt_period=0.001）→ sendCommand(JointPosition)
                                    反复发**同一个**最新值，直到我更新它
                                    0.25 秒拿不到新目标 → 刹车 latch
```

三件必须知道的事：

- **两个模式互斥**。RT 模式下 `Move*` 被拒（ec=262），Nrt 模式下 `sendCommand` 无效。这就是切换要走三步（停发送线程 → `stopMove()` → `setMotionControlMode`）的原因。
- **「实时」是控制器侧的保证，不是我们侧的**。我们跑在普通 Linux 上，没有 RTOS，抖动进不去这个保证。
- 这台 AR5 的 **RT 笛卡尔模式是死的**（收指令不动），所以 RT 路径只能发关节角 —— 逆解必须我们自己做。

## 3. 覆盖式跳过中间值，会不会跳跃？

**不会，因为发的是「绝对位置」不是「位移增量」。**

关键在这里：

```
发增量:  臂 += Δ    ← 丢一帧就永久少走一段，会累积误差
发绝对:  臂 → P     ← 丢一帧只是这一刻的目标粗了点，下一帧就补回来
```

臂也不会瞬移 —— 它收到新目标后是**伺服过去**的，中间的空间位置照样连续经过。丢掉的不是「运动」，只是「这段运动的描述精细度」。

**但有个前提，跳过了会真出事**：相邻两个设定点之间的差必须在臂一个周期内够得着。够不着的话，伺服想一帧内消掉大误差 → 速度尖峰 → 驱动的 `joint_jump_max` 闸门直接拒解（就是之前刷屏的 `goal jumps ... refusing`）。

所以代码里有三道保险：

- 逆解里的 `max_step = max_joint_speed / hz` —— 之前写死 0.12 rad @50Hz = 6 rad/s，是臂上限 0.74 rad/s 的 **8 倍**，这就是「臂很抖」的一个根因
- 发送线程 1kHz 反复发同一个值，让控制器看到的是连续流
- `--max-lead` 缰绳

**对照提交任务式**：那边跳过一个点是**真的把路点从路径里删掉**，臂会直接切到下一个点、把角抹掉。遥操无所谓（我们要最新位置，不要手的精确轨迹），但如果是焊接、画线这种路径本身就是任务的场合，就不能这么跳。

## 4. 截止频率是什么，fc 是吗

**是。** fc = cutoff frequency。

定义：低通滤波器输出功率降到输入一半的那个频率（−3dB，幅度 ×0.707）。比它低的频率基本原样通过，比它高的越来越被压掉。

一阶低通的换算（代码里 [avp_arm_teleop.py:248-251](../../../../Project_Atom/遥操/VR设备/avp_arm_teleop.py#L248-L251) 就是这个）：

```
τ = 1/(2π·fc)        时间常数
阶跃输入：τ 走完 63%，3τ 走完 95%

fc = 1Hz   → τ = 159ms     ← One-Euro 静止时就是这个
fc = 10Hz  → τ = 16ms
```

为什么这个值是个两难：

```
人的**有意识**手臂动作     0 ~ 2 Hz
生理震颤 + 传感器噪声      5 ~ 20 Hz
```

固定 fc=1Hz 能杀掉震颤，但也把你 1~2Hz 的真实动作拖慢了 —— 这就是我上一轮算的「停手之后还要爬 10mm、花 340ms」。One-Euro 的做法是让 fc **每帧重算**（`fc = min_cutoff + beta·|速度|`），所以它不是一个固定滤波器，是个时变滤波器。

## 5. 关于路径生成的终点、起点、频率

三个地方要修正：

### ① 发给控制器的不是 delta，是**绝对位姿**

这是你自己定的架构（「用控制器去做绝对位姿推算」），代码就是这么实现的：

```
本地: p_target = ref["p_tool"] + R_follow @ R @ (手的位移) @ scale
                 └─ 接合那一刻的末端位置（基准）
      ↑ 这是一个**基座系下的绝对位置**，delta 在这里就已经被吃掉了
发给控制器: MoveLCommand(trans=p_target, rpy=...)
```

delta 只活在我们本地的一行算式里，控制器从头到尾只见过绝对位姿。

### ② 起点不是「臂上一刻的位姿」，是「上一段的终点」

这条很关键：

```
队列 [P1][P2][P3]，臂现在实际在 P1 和 P2 之间某处

append P4 时，规划器的起点是 **P3**，不是臂的实测位置
```

路径是一条**首尾相接的折线**，臂在这条折线上往前爬。这就是积压能形成的原因 —— 折线已经画到 P4 了，臂还在 P1 附近。

### ③ 不是 20ms 生成一次路径 —— 大部分帧根本没下发

上一轮实测（16 秒）：

```
共 597 帧（循环实际 ~37Hz，不是 50Hz —— sleep(0.02) 加上查状态的开销）
  下发        64 条    ← 只有这些才生成路径，约 4Hz
  跳过(死区) 440 帧
  跳过(前导)  93 帧
```

所以真实的画面是：

```
50Hz  采样手 → One-Euro → 算绝对目标        （每 20ms 一次）
        ↓  死区闸门 + 前导闸门（筛掉 ~90%）
 ~4Hz  moveAppend 一个路点                  （每 250ms 一次）
        ↓  控制器
1kHz  插补 + 逆解 + 伺服
```

## 6. 10Hz 调用会把 5 次 delta 合成一个大 delta 吗

**效果方向对了，机制是错的。**

MoveL **不会**合并那 5 次 —— 它**根本没见过**你没发的那 4 次。你只发了最新的那个绝对位姿，另外 4 个是被**丢弃**，不是被**累加**。（因为发的是绝对位姿，丢掉中间值不会少走路 —— 见问题 3。）

那为什么确实会更平滑？因为**段变长了**：

> 段一短，加速度限制就主导 —— 实测抖动路径上段长 ~1mm 时，臂只跑到 **25~33mm/s**，而指令是 250mm/s。段拉长，臂才提得起速，运动才连贯。

**但代价是两条，不是免费的：**

1. **延迟**：固定 10Hz 意味着哪怕你猛地挥一下手，这个动作也要等最多 100ms 才被下发。
2. **路径保真度**：100ms 内手的轨迹被一条直线代替，拐角被抹掉。

**这正是为什么我们用死区而不是降频率。** 死区是「自适应的降频」：

```
固定 10Hz:   不管动作大小，一律压 100ms   ← 快速大动作也被无谓地拖慢
死区 3mm:    小动作（=噪声）丢掉
             大动作（=真动作）**立刻放行，零滞后**
```

同样能把段拉长，但只对噪声下手。

## 7. 「频率越小越平滑」和它的反过来

### 前半句：方向对，但**不单调**，有最优点

```
太快（每帧都发）→ 段碎成 1mm → 加速度受限、臂爬不起来 → 卡顿 + 延迟
      ↓
   最优区间
      ↓
太慢（比如 2Hz）→ 段长到 100mm+ → 拐角全被抹掉、位置一跳一跳 → 看着**更不平滑**
```

我们扫出来的就是这条曲线：死区 0.5mm 是 73ms/跟踪RMS 19.7mm，3.0mm 是 37ms/14.2mm —— 往大调是改善的；但再往大一定会翻转成可见的台阶。

### 后半句：**不成立**

MoveL 调用频率固定的话，提高手的采样率**不会让执行更平滑** —— 多采的那些样本只会被丢掉（只发最新那个）。

提高采样率买到的是**别的东西**：

| 买到 | 为什么 |
|---|---|
| **更低的延迟** | 50Hz 时你发出去的样本最多已经陈旧 20ms；200Hz 只有 5ms |
| **更好的速度估计** | One-Euro 的 fc 靠速度算，速度估得准 → 同样的平滑度下滞后更小 |

而**执行路径的平滑度**由三件事决定，跟上游采样率无关：段长、转弯区、控制器 1kHz 插补 + 加加速度限制。

> 另外有个天花板：采样率超过头显自己的推流率就没有意义了，多出来的都是重复帧。

## 8. 插补周期是什么

控制器**重算一次指令关节角**的固定节拍。这台是 **1ms（1kHz）** —— 依据是 SDK 要求 `sendCommand` 必须 1ms 一帧，驱动里 `rt_period = 0.001` 也是照这个设的。

三层节拍：

```
规划层（每段一次）   给出 s(t)：时刻 t 该走到这条路径的哪个位置
      ↓
插补层（1kHz）      t = 0, 1ms, 2ms, ... 代进去
                    → 得到该时刻的笛卡尔位姿
                    → **做一次逆解** → 7 个关节角
      ↓
伺服层（更高）      关节角 → 速度环 → 电流环 → 电机
```

所以「插补」字面意思就是**在你给的两个点之间造点**。你 4Hz 给两个相隔 250ms 的路点，控制器会在中间造出 **250 个**中间位姿，每个都做一次逆解。

这就是为什么把逆解交给控制器会「丝滑不少」—— 不是它的逆解算得比我们好（我们的旋量法解析解 1.9ms、残差 0.0000mm，比它的 41ms RPC 强），而是**它做逆解的频率是我们的 250 倍**。

## 9. 臂角是 J 几？

**臂角不是任何一个 J —— 它不是关节，是一个「冗余参数」。**

AR5 是 S-R-S 构型（我从真实 DH 验过：肩 j0,j1,j2 交于一点、误差 0.23mm；腕 j4,j5,j6 交于一点、误差 0.32mm；中间 j3 是肘）：

```
        肩 S ●                        末端位姿一定 → 腕心 W 的位置就定了
            ┃╲                        |SE| 和 |EW| 是固定杆长
            ┃ ╲                       ⟹ 肘 E 只能落在**绕 SW 轴的一个圆**上
            ┃  ● 肘 E  ← 在圆上滑动
            ┃ ╱          TCP 完全不动
        腕 W ●
            ┃
           TCP
```

**臂角 ψ = 肘在那个圆上的角位置。** 它就是第 7 个自由度，改它只动肘、TCP 纹丝不动 —— 这正是「零空间/自运动」。

和 J3 的关系（容易混）：

| | 是什么 | 由谁定 |
|---|---|---|
| **J3（肘关节）** | 真实的一根轴，控制**肘的弯曲程度**，也就是 \|SW\| 有多长 | **末端位姿定死**（我推过 `\|v(j3)\|² = A + R·cos(j3−φ)`，精确到 3.3e-16） |
| **臂角 ψ** | 不是轴，是肘**绕 SW 轴转到哪** | **位姿定不住**，这就是冗余 |

所以给控制器的 `CartesianPosition` 要带三样：

```
trans + rpy   6 维位姿      → 定住 |SW| ⟹ 定住 j3 的大小
elbow         臂角 ψ        → 补上第 7 维
confData      离散解支      → 肩左右 / 肘上下 / 腕翻转（连续参数选不出来的那部分）
```

我们代码里是 `start()` 时从 `cartPosture()` 读出当前的 `elbow` 和 `confData`，之后每个路点都原样带上 —— 等于把肘钉死在接合时的位置，不让它自己换边。

> ⚠ 一点说明：`elbow` 字段承载的是臂角 ψ，这是 7 轴 SDK 的标准约定，也和「6 维位姿 + 1 个标量 = 完整构型」对得上；但**具体的角度定义（零位在哪、正方向）厂家文档里我没查到**，我们是原样读、原样传，没依赖它的具体数值含义。真要用它去主动调肘型（比如让肘避开障碍），得先标定这个约定。

## 3. 截止频率和 One-Euro 的关系

**你的总结是对的。** 补三点让它更准：

1. 不是「消除」是**衰减** —— fc 以上的频率被越压越狠，不是一刀切掉。
2. One-Euro 能成立，靠的是一个**相关性**：你最需要压抖的时候（手停着）恰好是速度最低的时候，你最不能忍延迟的时候（快速挥动）恰好速度最高。它就是拿速度当「现在该压多狠」的代理量。

## 4. delta 怎么变绝对位姿、怎么发、控制器回什么

### ① delta → 绝对位姿（纯本地，一行算式）

接合那一刻记下四个基准量，之后每帧：

```python
# 位置：手相对基准移了多少，末端就相对基准移多少
p_target = ref["p_tool"] + R_follow @ R @ (here - ref["p_hand"]) * args.scale
#          └ 接合时末端在哪    └ 坐标系变换 └ 手相对基准的位移

# 姿态：手相对基准转了多少，末端就相对基准转多少（共轭换系）
R_rel    = R @ (Rw @ ref["R_hand"].T) @ R.T
R_target = R_rel @ ref["R_tool"]
```

`R = yaw_matrix(--yaw) @ mirror` 是头显系→臂基座系的变换。**delta 只活在 `(here - ref["p_hand"])` 这一项里**，加到基准上之后就变成基座系下的绝对位姿了，控制器从头到尾没见过增量。

### ② 怎么发

```python
t = CartesianPosition(); t.trans = [...]; t.rpy = [...]
t.elbow = ...; t.confData = [...]        # 7 轴冗余，见第 14 题
cmd = MoveLCommand(t); cmd.speed = 250; cmd.zone = 3
robot.moveAppend(cmd, PyString("m42"), ec)   # TCP/IP RPC 到 192.168.2.160
```

`ec` 是个字典，**由 SDK 原地填错误码** —— 这就是「静默失败」的来源：失败不抛异常，你不查 `ec` 就什么都不知道。

### ③ 控制器回什么信号 —— **MoveL 没有完成回调，全靠轮询**

| 方式 | 接口 | 耗时 | 有没有用 |
|---|---|---|---|
| 拉：当前位姿 | `cartPosture()` | 0.177ms | ✓ 算前导距离靠它 |
| 拉：运动状态 | `operationState()` | 0.093ms | ✓ 判队列空不空靠它 |
| 拉：执行进度 | `queryEventInfo(moveExecution)` → `wayPointIndex` | 0.002ms | ✗ **批内下标**，单条 append 恒为 0，没法用 |
| **推**：实时状态流 | `startReceiveRobotState()` + `updateRobotState()` | — | 只在 RT 诊断里用（订阅 `q_m`/`q_c`/`pos_m`/`pos_c`） |

只有最后一条是控制器**主动推**给我们的，而且它是 RT 那条通道的东西。MoveL 这边没有「我干完了」的通知 —— 这正是「队列跑空了怎么知道」会变成一个问题的根源。

## 5. moveAppend、路点、4Hz

- **路点 (waypoint)**：一个目标位姿（`trans` + `rpy` + `elbow` + `confData`），是折线路径上的一个顶点。
- **moveAppend**：把一条运动指令（里面裹着一个路点）**塞进控制器的 FIFO 队列**。0.03ms 返回，**不执行、不阻塞**，纯入队。队列容量 `setMaxCacheSize(300)`。
- **moveStart**：开始消费队列。42.8ms 往返，返回时臂还没动。

> 严格说没有一个叫 `movel()` 的函数，是 `moveAppend(MoveLCommand(...))`。

**4Hz 就是 `moveAppend` 的实际频率**，实测来的：

```
16 秒里：共 597 帧循环（≈37Hz，不是 50Hz——sleep(0.02) 加上查状态的开销）
         下发        64 条   → 64/16 = 4Hz   ← 这就是「调用 movel 的频率」
         跳过(死区) 440 帧
         跳过(前导)  93 帧
```

## 6. 平滑和延迟为什么冲突；换 MoveJ 行不行

### 前半：这个冲突**不是普遍规律**，分情况

冲突只在**频率域**工具上成立：

> 任何因果滤波器，要压掉高频，输出就必须滞后于输入 —— 因为你不知道未来。这是硬的。

但**死区打破了这个权衡** —— 实测它同时改善了延迟（73→37ms）和跟踪精度（RMS 19.7→14.2mm）。为什么能两头赢：

```
噪声和真实动作在**频率**上重叠（都有低频成分）→ 滤波必然误伤 → 必须权衡
噪声和真实动作在**幅度**上分得开（0.82mm vs 几十mm）→ 死区可以精确只打噪声 → 不用权衡
```

所以准确说法是：**只要你要抑制的东西和你要保留的东西在某个维度上可分，就不必权衡。** 频率上分不开，幅度上分得开，那就用幅度工具。

### 后半：MoveJ 救不了路径保真度

| | MoveL | MoveJ |
|---|---|---|
| 在哪插补 | **笛卡尔空间** | **关节空间** |
| TCP 轨迹 | 直线 | **曲线**（不可预测） |
| 奇异点 | 会出问题（笛卡尔直线可能要求无穷关节速度） | 不受影响 |

SDK 里 `MoveJCommand` 也接受笛卡尔目标（我查了签名，四种重载，第一种就是 `CartesianPosition`）。

**但它解决不了你的问题，原因是：路径保真度的损失不是 MoveL 造成的，是「下发点太少」造成的。** 你丢掉的中间点，MoveJ 一样看不见。换成 MoveJ 只是把两点之间的**直线**换成一条**弯线**，对遥操来说保真度反而更差 —— 你盯着末端看，它却走一条你预料不到的弧。

想要保真度，唯一的办法是**多发点**。

## 7. 段为什么会变长

你说的机制不对 —— **和插值无关。**

段长 = **相邻两个「已下发路点」之间的距离**。插值发生在**段的内部**（控制器在两个路点之间造中间点），它改变的是执行点的密度，**不改变段的端点，也就不改变段长**。

段长只由一件事决定：**两次下发之间，手走了多远。**

```
手速 100mm/s：
  每帧都发 (50Hz)  → 每 20ms 发一次  → 段长 = 100 × 0.020 = 2mm
  每 5 帧发 (10Hz) → 每 100ms 发一次 → 段长 = 100 × 0.100 = 10mm
```

为什么段长要紧 —— **加速度限制**：

```
一段长度 d，加速度 a，要从静止加速再减速到位
  峰值速度 ≈ √(a·d)         ← 和 d 开根号成正比

d = 1mm  → 慢
d = 10mm → 快 √10 ≈ 3.2 倍
```

实测就是这个：段长 ~1mm 时臂只跑到 **25~33mm/s**，而指令是 250mm/s —— 每一段都还在加速阶段就结束了。

## 8. 有死区了还要截止频率吗

**要，而且顺序不能反。** 它们串联，各干一件对方干不了的事。

只用死区会踩四个坑：

1. **抖动幅度会超过死区**。头显原始抖动 ~3.04mm，你拿 3mm 死区去拦，一半都拦不住。得先靠 One-Euro 压到 **0.82mm**，3mm 死区才稳稳在噪声之上。不滤波的话你得开到 ~10mm 死区 —— 位置量化 10mm，没法用了。
2. **死区是非线性的，会产生「黏滞—跳跃」**。死区越大，台阶越明显。滤波的输出是连续的。
3. **死区不减小噪声，只是不下发**。噪声一旦把目标顶过阈值，**带着全部噪声的那个值**就被发出去了。滤波是真的把幅度压小。
4. **`rt` 后端根本没有死区**。它是覆盖式、每帧都发，滤波是那条路上**唯一**的降抖手段。

所以链条是：

```
原始 3.04mm  →[One-Euro]→  0.82mm  →[死区 3mm]→  只有真动作能过
              压幅度                   卡阈值
```

## 9. RMS 是什么；"拐角被抹掉"到底指什么

### RMS

Root Mean Square，均方根：`sqrt(mean(误差²))`。用一个数概括一整串误差，而且**对大误差惩罚更重**（平方的效果）。这里是臂的实际 x 位置 和 干净正弦目标 之间的偏差。

### 拐角 —— **你说得对，我上一轮的措辞不准，得拆成两件事**

MoveL 每一段确实都是直线，**命令路径上本来就没有拐角**。「拐角被抹掉」我指的其实是**你手的轨迹的拐角**，两个不同的机制：

**机制 A：弦代替弧（这是主要的，和下发频率有关）**

```
你手的真实轨迹是条曲线：      ╭──────╮
                           ╱        ╲

点密（高频下发）:  ╱╲╱─╲─╱╲   折线细密地贴合曲线，曲率保留下来
点疏（低频下发）:  ╱        ╲   只剩两条长直线，曲线顶部被一条**弦**切掉
                   ↑ 这里丢了
```

丢掉的不是「命令路径的拐角」，是**你手上那段圆弧再也没进过命令路径**。下发越疏，弦越长，切得越狠。

**机制 B：转弯区倒圆（和下发频率无关）**

命令折线**自己**的顶点，会被 3mm 的转弯区倒圆：

```
zone = 0:  A ──→ B(停) ──→ C     尖角，但一段一停
zone = 3mm: A ──→ ╰B╯ ──→ C      3mm 半径倒圆，连续
```

这个是我们主动要的（不然每个点都停一下），代价是精确到位的能力 —— 也正因如此，**队列的最后一个点永远是 fine 点**，不倒圆。

## 10. 平滑度三要素，是通用的还是 Nrt 专有

**是 Nrt 专有的 —— RT 换了一整套。** 这个区别很根本：

| | **Nrt（MoveL）** | **RT（关节流）** |
|---|---|---|
| 谁决定轨迹形状 | **控制器** | **我们**（每 1ms 的设定点序列本身就是轨迹） |
| 平滑靠 ① | **段长**（够长臂才提得起速） | **上游滤波**（One-Euro） |
| 平滑靠 ② | **转弯区**（段间倒圆，不一段一停） | **`max_step` 速率限制**（= `max_joint_speed/hz`） |
| 平滑靠 ③ | **控制器 1kHz 插补 + 加加速度限制** | **发送线程 1kHz 重发保持**（`rt_period=0.001`，反复发同一个最新值，让控制器看到连续流） |
| 还有 | `setDefaultConfOpt` 保证解支不跳 | `--gain` 伺服增益、`--max-lead` 缰绳 |

关键差别：

> **RT 模式下，你下游没有任何东西能救你。** 你发什么，臂就执行什么。所以「臂这条路上原来一点滤波都没有」在 RT 下是致命的 —— 噪声原样变成关节指令。
> **Nrt 下控制器是一道缓冲**：它会按自己的加速度/加加速度限制去平滑，哪怕你给的点很粗糙。

这也是为什么同样的手抖，movel 那条路感觉「丝滑不少」。

## 11. 「250 倍」是怎么算的

摊开算式，顺便说清楚它比的是**什么和什么**：

```
控制器每秒做的逆解次数 = 1 / 插补周期 = 1 / 1ms = 1000 次/秒
我们每秒下发的路点数   = 64 条 / 16 秒 = 4 条/秒
                                          ─────
                                     1000 / 4 = 250
```

**它比的不是两个求解器的速度，是「控制器在我们两个路点之间插了多少刀」。** 我们给它两个相隔 250ms 的点，它在中间造 250 个中间位姿，每个做一次逆解。

三条路的逆解次数摆一起看更清楚：

| | 我们本地逆解 | 控制器逆解 |
|---|---|---|
| `rt` 后端 | **50 次/秒**（`--hz 50`） | 0（它只收关节角，不用解） |
| `movel` 后端 | **0 次** | **~1000 次/秒** |
| 我们求解器的能力上限 | 1.93ms/次 → 理论 ~500 次/秒 | 41ms/次（RPC，见第 12 题） |

> ⚠ **1kHz 这个数是推断，不是我直接测的**。依据是 SDK 要求 `sendCommand` 必须 1ms 一帧，以及驱动里 `rt_period = 0.001`。控制器内部的插补周期我没有独立测过。

## 12. 解析解 vs 数值解；还有哪些；RPC

### 两类的本质区别

| | **解析解**（closed-form） | **数值解**（iterative） |
|---|---|---|
| 怎么算 | **代公式**，有限步 | 从初值**迭代逼近** |
| 耗时 | 确定（我们的 1.93ms） | 不确定，看收敛（2.65ms） |
| 精度 | 机器精度（残差 **0.0000mm**） | 看收敛判据（0.054mm） |
| 给几个解 | **全部解支**（理论最多 8 个） | **一个**，取决于初值 |
| 会不会失败 | 不会（无解就是真无解） | 会不收敛、近奇异会病态 |
| 适用范围 | **只有特定结构才有**（Pieper 条件：三轴交于一点 或 三轴平行） | 任意结构 |
| 加约束 | 难（公式里塞不进限位/平滑偏好） | **容易**（box 约束、加权代价、零空间偏好） |

我们四个求解器正好覆盖这两类（都在 [ar5_ik.py](ar5_ik.py) / [ar5_poe_ik.py](ar5_poe_ik.py)）：

| 类 | 实现 | 耗时 | 残差 |
|---|---|---|---|
| 解析 | `AR5PoeIK`（旋量法 + Paden-Kahan） | 1.93ms | 0.0000mm |
| 解析 | `AR5SrsIK`（从 DH 推的闭式） | — | — |
| 数值 | `AR5OptIK`（L-BFGS-B 加权代价 + box 约束）**默认** | 2.65ms | 0.054mm |
| 数值 | `AR5IK`（DLS 雅可比迭代，旧的） | — | — |

### 除了旋量法，解析解还有哪些路子

- **DH 代数消元法**（Paul 法）：直接对 DH 变换矩阵两边左乘逆矩阵，消元凑出单变量方程。`ar5_srs_ik.py` 走的就是这条。
- **Pieper 法**：专治「末三轴交于一点」的球腕，把**位置和姿态解耦** —— 先用位置解前三轴，再用姿态解后三轴。
- **旋量法 (PoE, Product of Exponentials) + Paden-Kahan 子问题**：把 IK 拆成几个**标准几何子问题**，每个都有闭式解：
  - 子问题 1：绕一根轴转，把点 p 转到 q
  - 子问题 2：绕两根相交的轴转，把 p 转到 q
  - 子问题 3：绕一根轴转，使点 p 到点 q 的距离等于 d
  
  我实现的是这条。好处是**几何意义清楚、不依赖 DH 参数化的奇怪约定**。
- 四元数 / 对偶四元数法。

数值侧还有：雅可比转置法、伪逆法、**DLS（阻尼最小二乘）**、CCD、FABRIK、SQP/L-BFGS 优化法、QP 法（比如 TRAC-IK 是「牛顿法 + SQP」双线程赛跑）。

### RPC

**Remote Procedure Call，远程过程调用** —— 在本机调一个函数，实际执行在**另一台机器**上，参数和结果走网络。

这里指 `robot.model().calcIk()`：看着像本地函数，其实是把请求打包发给 192.168.2.160 的控制器，控制器算完回传。所以它 **41ms** —— 这 41ms 几乎全是网络往返 + 控制器端排队，**不是计算时间**。

> 同一个坑还有 `robot.checkPath`，也是 42ms RPC，而且**持 GIL**（见 [xcoresdk-python-holds-gil]）。50Hz 只有 20ms 预算，这种调用一次就爆表。

## 14. 肩 / 腕 / 肘 是 J 几

**肘对了，肩和腕不对 —— 它们各是三根轴，不是一根。**

AR5 是 **S-R-S** 构型（Spherical - Revolute - Spherical = 3 + 1 + 3 = 7），我从真实 DH 验过：

| 部位 | 1 基（你的写法） | 0 基（代码里） | 实测依据 |
|---|---|---|---|
| **肩**（球关节） | **J1, J2, J3** | j0, j1, j2 | 三轴交于 (0, 0, 0.1745)，误差 **0.23mm** |
| **肘**（单轴） | **J4** ✓ | j3 | 10.5mm 偏置 |
| **腕**（球关节） | **J5, J6, J7** | j4, j5, j6 | 三轴交于 (0, 0, 0.7845)，误差 **0.32mm** |

> ⚠ 命名陷阱：我们的参数 `--lock-j5` 用的是**0 基**（[avp_arm_teleop.py:1033](avp_arm_teleop.py#L1033) 是 `lock = {5: ...}`），所以它锁的是**第 6 根轴 = J6**，不是 J5。

### 零空间那段

你的描述对，补两个术语上的精确性：

```
末端位姿定死 → 腕心 W 位置定死
|SE|、|EW| 是固定杆长 → 肘 E 只能落在**绕 SW 连线的一个圆**上
沿这个圆滑动 → TCP 纹丝不动
```

- **这个圆**叫 **自运动流形**（self-motion manifold）—— 位置层面的概念，是所有「TCP 相同」的构型集合。
- **零空间**严格说是**雅可比矩阵的零空间**：满足 `J·q̇ = 0` 的关节速度方向集合，也就是「不产生末端速度的关节运动方向」—— **速度层面**的概念。7 轴解 6 维，零空间维数 = 7 − 6 = **1**。
- **臂角 ψ** 就是这一维的参数化：肘在圆上转到哪。

两者一一对应：沿零空间方向积分，走出来的轨迹就是自运动流形上那个圆。

**和 J4 的区别**（这是最容易混的一点）：

| | J4（肘关节） | 臂角 ψ |
|---|---|---|
| 是什么 | 一根**真实的轴** | 不是轴，是个**导出参数** |
| 控制什么 | 肘的弯曲程度，即 \|SW\| 有多长 | 肘绕 SW 轴**转到哪** |
| 谁定的 | **末端位姿定死**（我推过 `\|v(j3)\|² = A + R·cos(j3−φ)`，精确到 3.3e-16） | **位姿定不住** —— 这就是冗余本身 |

所以 `CartesianPosition` 要带三样才完整：`trans+rpy`（6 维，定住 \|SW\| ⟹ 定住 J4 大小）+ `elbow`（臂角 ψ，补第 7 维）+ `confData`（离散解支：肩左右/肘上下/腕翻转）。

## 1. RT 和 RTC —— 它们不是两个方案，是同一条路上的两步

你可能是把它们当成「二选一」了。不是的：**要用 RT，这两个你都得碰，先后顺序固定。**

```
第一步：切模式          「从现在起我们按实时方式干活」
        setMotionControlMode(RtCommandMode)
        ↑ 这是一个**状态**，是臂的一个属性，不是个东西

第二步：拿操作句柄       「给我实时模式下的那套按钮」
        rtc = robot.getRtMotionController()
        ↑ 这是一个**对象**，之后所有实时操作都从它身上调

第三步：用它干活
        rtc.startMove(...)    rtc.sendCommand(...)    rtc.stopMove()
```

打个比方：

> `setMotionControlMode(RtCommandMode)` = 把电视**切到 HDMI 输入**
> `getRtMotionController()` = 拿到**接在 HDMI 口上那台播放机的遥控器**
>
> 没切输入源，遥控器按了也没画面；切了输入源不拿遥控器，也什么都放不出来。

为什么 SDK 要分成两个？因为「模式」只有一个值（是/否实时），而「实时模式下能做的操作」有一大堆（开始、发指令、设滤波、停止……）。把操作打包到一个对象上，比全塞在 `robot` 上干净。

**Nrt 那边没有对应的东西** —— `moveAppend`/`moveStart` 直接挂在 `robot` 上。这也是它俩看起来不对称的原因。

## 2. 四个字段各是什么

先修一个用词：**「位姿」= 位置 + 姿态**（pose）。`rpy` 只是**姿态**（orientation）。

| 字段 | 官方说明 | 通俗讲 |
|---|---|---|
| `trans` | 平移量 [X,Y,Z]，米 | 末端在**哪** |
| `rpy` | 欧拉角 [Rx,Ry,Rz]，弧度 | 末端**朝哪** |
| `elbow` | **臂角，适用于 7 轴机器人，单位弧度** | 肘绕「肩—腕」连线转到哪（第 7 维） |
| `confData` | **轴配置数据，长度 8：[cf1…cf7, cfx]** | 用**哪一个解支** |

### confData 到底管什么

前三个字段（位置 + 姿态 + 臂角）定完之后，**关节角仍然可能有好几组**。因为有些差异是**离散的、跳跃的**，连续参数表达不了：

```
① 肘上 / 肘下          手肘朝上撑着，还是朝下垂着
② 肩部翻转            手臂从身体这侧绕过去，还是那侧
③ 腕部翻转            腕转 180°，同时 J5/J7 各转 180° —— 末端姿态一模一样，
                      但三个腕关节的角度完全不同
④ 每根轴的"圈数"       同一个角度，可以是 +30° 也可以是 −330°
```

理论上 2³ = **8 个解支**。`confData` 就是「用第几支」的编号。

> 我实测过这台臂的可达情况：**平均只有 3.15 个解支够得着，从来没有 8 个**。其中**腕翻转 0.00% 可达** —— 因为 J6/J7 只有 ±50°，翻 180° 根本转不过去；肘翻转 58% 可达，肩翻转 99% 可达。

**解支跳变是遥操的大敌**：从一支跳到另一支，臂必须甩一大圈（中间还要过奇异点）。人手动了 1mm，臂猛地翻一下 —— 这就是之前刷屏的 `goal jumps ... refusing`。

### 但我们其实没在用 confData

官方文档写得很清楚：

> `setDefaultConfOpt(forced)`：
> **true** — 用运动指令的 confData 算逆解，算不出就报错
> **false** — 不用，逆解时**选取机械臂当前轴角度的最近解**

我们设的是 **false**。所以：

- `confData` 我们照填（读出来什么填什么），但**控制器不看它**
- 分支选择完全交给控制器的「取最近解」
- 这正是遥操要的：永远选离当前姿态最近的那一支 ⟹ **永远不会跳支**

## 3. 「0.03ms 返回」和「42.8ms 往返」

这是三个不同的时间点，必须分清：

```
你调用函数 ──┬──────────────┬──────────────┬─────────────→ 时间
             ①              ②              ③
             函数还给你       控制器回话说    臂真的开始动
             控制权          "我收到了"      / 走到位
```

| | 指标 | 实测 | 说明 |
|---|---|---|---|
| `moveAppend` | **①调用返回** | **0.03ms** | 30 微秒。**比一次以太网往返还快**，所以它肯定没等控制器确认 —— 塞进去就走人 |
| `moveStart` | **②往返确认** | **42.8ms** | 请求发到控制器、控制器处理、回复传回来，一个来回 |
| `moveStart` | **③首次运动** | **127ms** | `moveStart` 返回的那一刻，**臂还一动没动**，还要再等 80 多毫秒 |

所以「非阻塞」在这里的准确含义是：**函数返回 ≠ 动作完成**。`moveStart` 虽然要等 42.8ms，但它等的是"控制器说收到"，不是"臂走完了"。真正走完要几百毫秒到几秒。

这也解释了为什么 `moveStart` 是个麻烦：**42.8ms 卡在遥操主循环里**（50Hz 只有 20ms 预算），而且它恰好发生在臂重新起步的瞬间 —— 人最能感觉到延迟的时刻。

> 我试过把它扔到工作线程上，**没用** —— xCoreSDK 的 Python 绑定整个调用期间不放 GIL，换个线程照样把主循环堵死（实测 5 秒里工作线程读 26503 次、主线程 1 次）。

## 4. 那 597 帧是怎么分掉的

主循环每秒转约 37 圈，每圈算出**一个目标位置**。这个目标要过**两道闸门**才能发出去。

### 闸门一：死区 ——「你几乎没动，我不发」

**为什么要拦**：你手停着的时候，头显给的数字还在抖（滤波之后还剩 0.8mm）。如果照单全收，就等于命令臂去**复刻这些抖动**。

而队列是「每个点都必须走完」的 —— 臂会老老实实一个一个去走那些抖动点。路径被切成毫米级的碎片，而**段一短臂就提不起速**（实测只跑到 25~33mm/s，指令是 250）。结果是：又抖、又慢、还堵着队列。

**怎么拦**：拿这一帧的目标，和**上一个真正发出去的目标**比。差不到 3mm，这一帧就当没发生过。

> 关键在「上一个**发出去的**」，不是「上一帧」。所以你缓慢移动时，差距会一点点**累积**，攒够 3mm 就发一次。**一点运动都不会丢**，只是被量化成 3mm 一跳。这也是为什么实测缓慢走 6mm，最后精准到 6.01mm。

### 闸门二：前导 ——「臂还欠着债，我不加新单」

**为什么要拦**：队列是只进不出的任务清单。你发得比臂走得快，清单就越排越长，臂永远在执行 200ms 之前的目标 —— **这就是延迟**。

**怎么拦**：每帧量一下「最后发出去的那个目标」离「臂现在实际在哪」有多远。超过 12mm（= 250mm/s × 50ms 的延迟预算），说明臂手上还压着 50ms 的活。这时候再塞新点只会让债更多，所以先不发，等它追近了再说。

### 为什么「跳过」不等于「丢失」

因为我们发的是**绝对位置**，不是「往前挪多少」。

```
发增量：丢一帧 = 永久少走一段，误差会累积  ✗
发绝对：丢一帧 = 这一刻的目标粗了点，下一帧直接给最新的  ✓
```

臂追上来之后，下一次发的是你**当下最新的**位置。中间跳过的那些中间值，本来也没人关心 —— 你要的是"手现在在哪"，不是"手走过的每一个脚印"。

### 所以那 16 秒的账是

```
597 帧
 ├─ 440 帧（74%）  你手基本没动，或者只是在抖    → 死区拦下
 ├─  93 帧（16%）  臂还在追前一个目标，债没还清  → 前导拦下
 └─  64 帧（11%）  真的动了，而且臂跟得上        → 发出去
```

只有约 **1/9** 的帧变成了真正的命令。其余的要么是噪声，要么是"现在发也没用"。

## 5. 「多发点 → 段变短 → 不影响卡顿」—— 最后半句错了

前面几步都对：

- 路径保真要多发点 ✓
- 多发点 = 调大下发频率 ✓
- 下发频率高 → 段长变短 ✓

**但「段变短不影响卡顿」正好说反了 —— 段短恰恰就是卡顿的原因。**

```
段长 1mm   → 臂还在加速阶段就到头了 → 实测只跑到 25~33mm/s（指令 250）
段长 10mm  → 有空间加速起来 → 快约 3 倍  （峰值速度 ≈ √(加速度 × 段长)）
```

另外「没执行的都丢了」这句在**提交任务式**里也不成立：

> **进了队列的点，一个都不会丢，每个都必须走完。** 这就是队列语义的定义。
> 会丢的是被**闸门拦在下发之前**的那些（死区/前导），它们根本没进过队列。

### 完整的权衡

```
下发频率 ↑ → 段长 ↓ → ✓ 路径保真度高（折线细密贴合手的轨迹）
                     → ✗ 臂提不起速，段间频繁切换 → 卡顿
                     → ✗ 队列积压 → 延迟涨

下发频率 ↓ → 段长 ↑ → ✗ 保真度低（长弦切掉手轨迹的弧）
                     → ✓ 臂跑得起来，顺
                     → ✗ 每次等得久 → 延迟也涨
```

**两头都有坏处，所以中间有个最优点。** 我们扫出来死区 3mm（对应约 4Hz 下发）就在这个最优区间附近。

而**死区比"固定降频"聪明在于：它不是无差别降频**。

```
固定 10Hz：  不管你是在抖还是在猛挥，一律压 100ms   ← 真动作也被无谓拖慢
死区 3mm：   抖动（小幅）→ 拦下
             真动作（大幅）→ **立刻放行，零滞后**
```

等于「该密的时候密，该疏的时候疏」——同样把段拉长了，但只对噪声下手。

## 6. 为什么 RT 下滤波这么关键

先修正我上一轮的说法：**严格讲不是"唯一可能"，而是"唯一实现了的"，而且它在 RT 下确实更合适。** 理由不是没有别的工具，是别的工具在 RT 下会**帮倒忙**。

根本区别在**下游有没有人给你兜底**：

```
Nrt:  你给几个路标 → 【控制器规划器】→ 执行
                      ↑ 这一层会按加速度/加加速度限制，
                        把你粗糙的输入重新抹成一条平滑轨迹

RT:   你给的每 1ms 一个点，**本身就是轨迹** → 执行
                      ↑ 没有这一层。你给什么形状，臂就走什么形状
```

所以在 RT 里，任何抖动要么在发出去之前被处理掉，要么就原样进关节。

**那 RT 里能不能也用死区？能，但效果差：**

```
Nrt + 死区：  目标一跳 3mm → 控制器用 1kHz 插补把这 3mm 抹成平滑一段 → 感觉不出来
RT  + 死区：  目标一跳 3mm → 关节指令直接阶跃 3mm → 下游没人抹平
                            → 要么被 max_step 限速拉成一条生硬的等速斜坡（加加速度无穷）
                            → 要么直接冲击
```

死区的输出是**离散台阶**，Nrt 下游有人给你倒圆，RT 下游没有。而滤波的输出是**连续**的，天然适合直接当轨迹用。

一句话：**Nrt 下你可以交粗活，因为控制器会精加工；RT 下你交出去的就是成品。**

## 7. DH 是什么

**Denavit-Hartenberg 参数** —— 描述串联机器人几何结构的标准方法。

核心思想：相邻两根轴之间本来需要 6 个数才能描述（3 平移 + 3 旋转）。DH 通过**巧妙地规定坐标系怎么摆**，把它压到 **4 个数**：

| 参数 | 符号 | 意思 |
|---|---|---|
| 连杆长度 | **a** | 沿公垂线，上一根轴到这根轴有多远 |
| 连杆扭角 | **α** | 上一根轴要绕公垂线转多少度才和这根轴平行 |
| 连杆偏距 | **d** | 沿上一根轴方向偏移多少 |
| 关节角 | **θ** | 绕这根轴转多少 ← **转动关节里这个是变量** |

所以 7 轴臂 = **7 × 4 = 28 个数**，几何结构就完全定死了。

**正解（FK）**就是把 7 个 4×4 变换矩阵连乘：`T = T₁·T₂·…·T₇`。

### 为什么这事对我们重要

厂家没给 AR5 的几何参数。我写了 [read_dh.py](read_dh.py) 从控制器把真实 DH 读出来存进 `ar5_dh.json`，有了它才能：

- **验证结构**：算出肩部三轴交于 (0,0,0.1745) 误差 0.23mm、腕部三轴交于 (0,0,0.7845) 误差 0.32mm → 确认是 S-R-S 构型 → **才知道存在闭式解**
- **推导解析解**：旋量法和 Paden-Kahan 子问题都要精确几何
- **自查**：PoE 正解 vs DH 正解对得上 4.4e-16，说明两套推导都没写错

> ⚠ 一个坑：DH 有**两种约定** —— 标准 DH（Denavit-Hartenberg 原版）和改进 DH（Craig 版），参数的挂载顺序不一样。混用会算出完全错误的结果，而且错得很隐蔽。

## 8. RT + 控制器逆解 vs Nrt + 控制器逆解

这两个都让控制器做逆解，区别在**控制器还额外干了多少活**：

| | **RT + 控制器逆解**<br>(`cartesianPosition`) | **Nrt + 控制器逆解**<br>(`MoveL`) |
|---|---|---|
| 你发什么 | 每 **1ms** 一个位姿设定点 | 偶尔一个路点（我们实测 4Hz） |
| 控制器做什么 | **只做**：位姿→关节角 + 伺服 | 路径生成 + 速度规划 + 插补 + 逆解 + 伺服 |
| 谁决定轨迹形状 | **你**（你的设定点序列就是轨迹） | **控制器** |
| 语义 | 覆盖式 | 队列式 |
| 延迟 | **1 个周期（1ms）** | 队列深度决定（我们 37ms） |
| 平滑谁负责 | **你** | **控制器** |
| 频率要求 | 硬性 1ms，慢了判丢包 | 随意 |
| 这台 AR5 | **不可用**（收指令但不动） | 可用 |

一句话概括：

> **RT 模式下控制器只帮你做「位姿 → 关节角」这一步换算，轨迹还是你自己的。
> Nrt 模式下控制器连轨迹一起替你规划了。**

比喻：

- **RT + 控制器逆解** = 你自己开车，每秒 1000 次决定方向盘转多少，只是"方向盘角度→轮子角度"的换算让车帮你算
- **Nrt** = 你只说"去那个路口"，**怎么走、怎么加减速、怎么过弯，全是车的事**

值得说一句：**RT + 控制器逆解本来是遥操的理想解** —— 1ms 延迟、不用本地逆解、控制器还帮你选最近解支。这正是我当初花那么多工夫去试它的原因。可惜实测这台臂上它收指令但不产生运动（20mm 指令实到 0.4mm，而且不随指令变），彻底死掉，才退到现在这两条路。
