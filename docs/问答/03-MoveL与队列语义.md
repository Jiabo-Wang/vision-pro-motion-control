查排队路径的接口语义：

`zone`（转弯区）能让相邻 MoveL 混合，`WaypointIndex` 能查队列执行到哪。而第 469 行那句话直接讲的就是**流式短轨迹**：

这条路的配套接口比我想的完整得多：

| 接口 | 作用 |
|---|---|
| `setDefaultConfOpt(false)` | **逆解时选取离当前轴角度最近的解** ← 正是你要的分支判据 |
| `setMaxCacheSize(1~1000, 默认300)` | 控制器侧路点缓冲，注释明说是**给流式短轨迹用的** |
| `zone` 转弯区 | 相邻 MoveL 混合，不会一段一停 |
| `adjustSpeedOnline(scale)` | 运行中动态调速 |
| `WaypointIndex` | 查队列执行到第几个点 |

关键未知数是 **`moveAppend` 的延迟**（之前那个 42ms 是 `checkPath`，不是同一个调用）。而这个**可以零位移测**——只 append 不 start，队列不执行：

**可行，而且我之前的一个关键假设是错的。**

`moveAppend` **中位 0.03ms**（批量摊到 0.02ms/条）。不是 42ms —— 那个数是 `checkPath` 的，我一直把两者混为一谈，导致整条排队路径被我提前判了死刑。

| | 延迟 |
|---|---|
| `checkPath`（可达性校验） | 42 ms |
| **`moveAppend`（下发指令）** | **0.03 ms** |
| 厂家 `calcIk`（RPC） | 41 ms |
| 本地旋量解析解 | 1.93 ms |

`moveAppend` 比我们现在的本地逆解还快 **60 倍**——它只是往队列里塞，规划和逆解都在控制器上异步做。

## 你这个思路的完整形态

```
头显 → 本地算绝对目标位姿 → moveAppend(MoveL, zone=转弯区) → 控制器做逆解+规划+执行
```

配套接口厂家都给齐了：

| 接口 | 作用 |
|---|---|
| `setDefaultConfOpt(false)` | **逆解选离当前轴角最近的解** ← 正是你要的分支判据，厂家内置 |
| `setMaxCacheSize(1~1000, 默认300)` | 控制器侧路点缓冲，注释明说**给流式短轨迹用** |
| `zone` 转弯区 | 相邻 MoveL 混合，不会一段一停 |
| `adjustSpeedOnline(scale)` | 运行中动态调速 |
| `WaypointIndex` | 查队列执行到第几个点 → **能管队列深度** |

而且有个很强的旁证：**示教器能对这台臂做笛卡尔点动和 MoveL**，说明控制器完全会算 AR5 的笛卡尔逆解。之前 RT 笛卡尔失败是那条通道的问题（`pos_c` 根本不更新），不是控制器不会算。

## 但有个真问题：队列延迟

排队是**异步**的。50Hz 塞进去，臂按自己的速度执行，**队列会堆积**——堆多深，手到臂的延迟就有多大。这是遥操的死穴。

管法是现成的：用 `WaypointIndex` 查执行到哪，队列超过 N 个点就**不再 append**（丢掉这一帧的目标，反正下一帧就有新的）。本质是把"绝对目标"当成可覆盖的最新值，而不是必须执行的轨迹。

## 三件要实测的

1. **MoveL 对 AR5 到底动不动**（RT 笛卡尔不动，排队式必须单独验）
2. **端到端延迟**：append 到臂真的动，差多少毫秒
3. **连续流式下能不能不停**：持续 append + `zone` 混合，看会不会一段一停

这三条一个脚本就能测完，前两条可以先用很小的位移。要我做吗？做的话还是独立脚本，不碰现有代码。

如果这条通了，架构会简单很多：本地只管坐标变换和绝对目标，**逆解、规划、限位、奇异全交给控制器**——我那些步长闸、跳变闸、限位势垒、奇异减速全都可以删掉。

## 能动，而且精确

**控制器完全会算 AR5 的笛卡尔逆解。** 之前 RT 笛卡尔不动，是那条通道的问题，不是控制器不会——这一点现在有正面证据了。

## 但流式下发会积压，延迟失控

50Hz 连续下发正弦（±25mm，10 秒，323 条，append 零错误）：

| t | 实测 x | 期望 x |
|---|---|---|
| 1.0s | +15.63 | +24.95 |
| 2.3s | +24.92 | −9.71 |
| 4.8s | −24.70 | +23.91 |
| 8.6s | −24.89 | +20.01 |

判据在最后一行：**停止下发之后 0.4 秒内臂还走了 21.12mm** —— 队列里全是积压。

## 根因是架构性的，不是调参能解决的

`moveAppend` 是**队列语义**：每条都是"必须执行的轨迹段"。50Hz 塞进去、臂按 150mm/s 执行，塞的比走的快，队列只会越积越深，延迟无上界。

而遥操要的是**覆盖语义**：最新的手部位姿应该**作废**前一个目标，不是排在它后面。

我试过用 `WaypointIndex` 管队列深度，但实测 `queryEventInfo` **返回的全是空值**（`cmdID` 空、`reachTarget` 恒 False、`wayPointIndex` 恒 0），拿不到队列进度，没法做背压。可能要 `setEventWatcher` 回调才填，但那又回到 GIL 的老问题。

还有一条硬伤：**127ms 的启动延迟**。遥操能接受的手到臂延迟大概 50ms 量级。

## 三条路的完整结论

| 路子 | 能动 | 延迟 | 可流式 | 结论 |
|---|---|---|---|---|
| RT 笛卡尔 | ✗ | — | — | 指令不进规划器 |
| MoveL 排队 | **✓ 精确** | 127ms 启动 + 队列积压 | ✗ 队列语义 | 单点定位可以，遥操不行 |
| **RT 关节 + 本地逆解** | ✓ | 1.93ms | ✓ 覆盖语义 | **现在这条** |

RT 关节模式的 `sendCommand` 是**覆盖语义**（发新的就顶掉旧的），这正是遥操需要的，而 MoveL 的队列语义天生不是。

所以架构不变：本地算绝对目标 + 旋量解析逆解 + RT 关节下发。

## 过程中我修正了自己两个错

1. **`moveAppend` 是 0.03ms 不是 42ms** —— 我一直把它和 `checkPath` 混为一谈，害得这条路被提前判死。值得测。
2. **流式必须"先 append 再 moveStart"** —— 反过来队列是空的，start 立刻结束，后面塞的没人执行（第一次测时臂完全没动就是这个）。

`try_movel_stream.py` 保留着，独立脚本，以后要做**点位示教**（非遥操）这条路是好用的：精确、控制器管限位奇异、0.03ms 下发。

## MoveL 路径点：确认可用

```
一次 moveAppend 塞 19 个路点（三角波 0→+25→−25→0 mm）
  append 耗时 0.44ms   ec=0
```

- 一次 `moveAppend` 最多 **100 个同类型指令**
- `zone` 转弯区让相邻段混合，不会一段一停
- 示例 `move_example.cpp:603` 就是这个用法（多段直线轨迹）

## 但 `wayPointIndex` 是**批内**下标，不是全局队列位置

这是我连错两次的根因。批量塞 19 个点时它 0→18 走得好好的；**单条单条塞**的时候，每条都是独立指令、各自只有 1 个路点，index 恒为 0。所以我那个 `depth = sent − wp − 1` 从第一帧起就是错的——刚才这轮又栽了一次（下发 8 条、跳过 473 条）。

而且我传的 `cmdID`（`PyString("batch1")`）也没被回显，返回的是自动生成的 `'l#0'`。所以**跨批次的队列进度拿不到**。

能拿到的只有「当前这一批执行到第几个点」。这只支持**双缓冲**模式：塞一批 N 点 → 看 index 快走完 → 塞下一批。延迟下限 = 一批的执行时长。N=4、50Hz 的话约 80ms。

## 所以对遥操还是不行，但理由变了

| | RT 关节（现在） | MoveL 路径点 |
|---|---|---|
| 语义 | **覆盖**（新指令顶掉旧的） | **队列**（每条都要执行完）|
| 延迟 | 本地逆解 1.93ms，立即下发 | ≥80ms（双缓冲）+ 127ms 启动 |
| 逆解 | 本地旋量解析解 | 控制器（`setDefaultConfOpt(False)` 取最近解）|

遥操要的是「最新的手部位姿作废前一个目标」，MoveL 天生做不到这件事。

## 但这条路对**别的事**很好用

既然确认了精度（20mm→20.00mm）、速度（0.44ms 塞 20 点）、连贯性，那么：

- **轨迹回放 / 示教点位**：本地算好一整条路径，一次塞进去，控制器管逆解+限位+奇异
- **原子动作的固定段**（比如你要做的抓取动作里"移到预抓取位"那一段）
- **标定流程**：走一串已知点

这些场景没有"最新覆盖"的需求，MoveL 路径点比自己算关节流要省事得多。

要不要我把这几轮硬件实验的结论写进记忆？信息量不小（RT 笛卡尔死路、moveAppend 0.03ms、模型库是通用 KDL 只是被白名单拦、MoveL 路径点可用但队列语义），下次不用重测。

## 问 4

> 遥操的频率和臂执行的频率分别是多少


一条链上有**五个不同的频率**，而且它们不匹配正是抖动的来源之一。

## 完整的频率链

| 环节 | 频率 | 来源 |
|---|---|---|
| 头显推流 | **~30 Hz** | Tracking Streamer（mock 实测 29.9Hz，真机没量过）|
| **遥操主循环** | **50 Hz** | `--hz` 默认 50 |
| 逆解（IK） | **50 Hz** | 每次 `env.step()` 调一次 |
| 灵巧手下发 | **40 Hz** | `--hand-hz`，独立线程（CAN 带宽限制）|
| **RT 发送线程 → 臂** | **1000 Hz** | `config.rt_period = 0.001` |
| 控制器伺服 | **1000 Hz** | SDK 文档：「控制器执行命令的周期为 1ms」|

实际跑起来的实测值（mock 端到端）：`[臂 50Hz  手 40Hz]`。

## 三处不匹配，每一处都有后果

**① 头显 30Hz → 主循环 50Hz**

主循环比数据源快，**约 40% 的迭代拿到的是同一帧**。代码里有 `frame is not prev_frame` 的判断，重复帧不会重复触发，但意味着**有效跟踪率其实是 30Hz**，不是 50Hz。

**② 主循环 50Hz → RT 发送 1kHz**

这中间是**发送线程在做插值**：它按 `joint_goal_step` 限速，朝 `_q_goal` 平滑逼近。所以臂实际执行的是 1kHz 的平滑流，不是 50Hz 的阶梯。

**③ 速度上限：42°/s vs 厂家的 120~200°/s**

```
config.max_joint_speed = 0.74 rad/s = 42°/s
厂家 setScale 文档给的各轴上限: 120,120,180,180,200,200,200 °/s
```

保守了 **3~5 倍**。注释里写了理由（从 0.25 m/s 提到 0.5 m/s，再高会抖），但那是**提高之前**的测试，而且当时臂这条路上**还没有任何输入滤波**（One-Euro 是后来才加的）。

## 和抖动的关系

我之前查出「指令比臂快 8 倍」（`max_step=0.12 rad @50Hz = 6 rad/s` vs 执行 0.74 rad/s），已经改成自动取 `max_joint_speed / hz = 0.0148 rad`。

但**有效跟踪率只有 30Hz** 这一条我之前没意识到——这意味着：

- 每 33ms 才有一个真实的新目标
- 中间那些循环在重复处理同一帧
- 如果头显的帧间隔本身不稳（我量过 ping 抖到 407ms），到达就是**成批的**，臂会一顿一顿

这一条 `--jitter-probe` 测不到（它测的是空间抖动），要等头显连上跑 `probe_hand_data.py` 才能确认——那个脚本的第二项就是**帧到达间隔**统计。

## 可以调的三个旋钮

| 想改什么 | 怎么调 |
|---|---|
| 主循环别空转 | `--hz 30` 对齐头显，省掉 40% 无效迭代 |
| 臂跟得更快 | `config.max_joint_speed` 往 0.74 以上提（**慎重**，要一步步来） |
| 手更跟手 | `--hand-hz` 往上，但受 CAN 带宽限制 |

真机上头显的实际帧率我**没测过**，上面 30Hz 是 mock 的数。连上之后跑 `probe_hand_data.py` 会给出真实帧率和到达间隔——那两个数决定了后面该怎么调。

## 问 8

> 提交任务式和流式覆盖式有什么区别

## 两种语义的区别

| | 提交任务式（MoveL 队列） | 流式覆盖式（RT 关节 sendCommand） |
|---|---|---|
| 一条指令是什么 | **一个必须执行完的任务** | **当前的目标值** |
| 新指令来了 | **排在旧的后面** | **顶掉旧的** |
| 发快了会怎样 | 队列堆积，**延迟无上界** | 没影响，只是中间值被跳过 |
| 能撤销单条吗 | 不能，`moveReset` 一清全清且停车 | 不存在这个问题 |
| 队列空了 | 臂停车，恢复要 **42.8ms** | 不存在队列 |

打个比方：**提交任务式是快递下单**——每一单都得送到，你连下 100 单，第 100 单要等前 99 单送完。**流式覆盖式是直播画面**——新帧盖掉旧帧，永远只播最新的。

对遥操来说这是要害：**你手在 t 时刻的位置，让 t−1 时刻的位置作废了**。队列语义却强迫机械臂去走那些已经过时的点——这就是第一次流式测试里跟踪误差 34mm、停止下发后臂还自己走了 21mm 的原因。

我的做法是**用"不提交"来模拟"覆盖"**：算出前导距离，超过预算就**直接丢掉这一帧**，不往队列里塞。丢掉的目标反正下一帧就有更新的。队列因此始终很浅，延迟就控住了（实测 59ms）。

三个症状都到底了。总结一下这轮改了什么、为什么：

**1. 动两下就不动了** —— 判「臂停没停」的方式错了。改成问控制器 `operationState`（0.093ms/次，每帧查得起）。实测它比位置**晚 87ms** 才退出 `moving`，永远不会在臂还动时说 idle，正是要的方向。`moveStart` 失败从 20 次降到 **0**。

**2. 速度太快** —— 400 → **250mm/s**。

**3. 延迟依旧很高** —— 根因不在速度，在**臂在追手抖**。One-Euro 之后还剩 0.82mm 残余抖动，原来 0.5mm 的死区拦不住，这些抖动被原样塞进队列；而排队式是每个点都必须走完的，**短段还是加速度受限的**（指令 250mm/s，抖动路径上臂实测只有 25~33mm/s）。把死区提到 3mm 后：

| | 延迟中位 | p95 | 跟踪RMS | 缓慢走6mm |
|---|---|---|---|---|
| 死区 0.5mm | 73ms | 114ms | 19.7mm | 实到 3.79mm |
| **死区 3.0mm** | **37ms** | 93ms | **14.2mm** | **实到 6.01mm** |

死区不但没吃掉精细动作，反而让精细动作更准 —— 它是对**上一个已下发点**的增量阈值，慢速运动会累积过阈，一个都不丢。
