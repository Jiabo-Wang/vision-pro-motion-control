## 问 1

> 看一下连接的相机是否是RGBD


我先做只读探测，不动任何设备。

**不是 RGBD，是两个普通 RGB 网络摄像头。**

## 探测结果

| 项 | 结果 |
|---|---|
| USB ID | `0c45:636b` Microdia — UGREEN Camera 1080P ×2（Device 008 / 009） |
| 驱动 | `uvcvideo`（标准 UVC 摄像头类） |
| 像素格式 | 只有 `MJPG` + `YUYV 4:2:2` |
| 深度相机模块 | 无（`lsmod` 里只有 uvcvideo，没有 realsense/orbbec/kinect） |
| 深度 SDK | 无（librealsense / libOrbbec / k4a 都不存在） |

判据很直接：**UVC 里没有任何深度流格式**。真正的 RGBD 相机（RealSense D4xx、Orbbec Astra/Femto、Kinect）要么会枚举出 `Z16`/`INVZ` 之类的深度像素格式，要么根本不走 uvcvideo 而是自己的内核模块 + SDK。这里两台都只吐 MJPG/YUYV，纯彩色。

四个 `/dev/video*` 节点也不是「彩色+深度」，而是每台相机各占两个：`video0`/`video2` 是 Video Capture（图像），`video1`/`video3` 是 Metadata Capture（UVC 元数据，`Device Caps` 里没有 Video Capture）。

## 一个会踩的坑

两台相机的序列号都是 `SN0001`（厂商没烧唯一序列号），所以 `/dev/v4l/by-id/` 只剩一条链接，指向 video2 —— **另一台在 by-id 下完全不可见**。要稳定区分这两台必须用 by-path：

- 相机 A（USB 口 10.3）→ `/dev/v4l/by-path/pci-0000:0d:00.0-usb-0:10.3:1.0-video-index0`
- 相机 B（USB 口 10.4）→ `/dev/v4l/by-path/pci-0000:0d:00.0-usb-0:10.4:1.0-video-index0`

注意 by-path 绑的是物理 USB 口，换口就会变。

## 我的首要怀疑：上一轮填的负载

**所以 `--payload` 已改成默认 0（不设）。** `--tcp-z` 保留 0.150 —— TCP 是纯几何量，不参与动力学，不会误触发碰撞。

我刚实测了 30 秒：**ping 47/47 全通**，端口一直是 **errno=111（连接被拒）**。111 的含义是「主机在线，但那个端口没人监听」。

你看到的 errno=11（超时）是**瞬时抖动**。这台头显的 Wi-Fi 会短暂掉线（之前量过 ping 抖动 5~407ms），而我的代码**单次探测就下结论**，一次没通就报「IP 不对」，把你指去查一个根本没问题的地方。

改成重试了：TCP 探 4 次、ping 探 3 次，并且区分三种结论：

```
✗ 192.168.0.246 **在线**（ping 3/3 通），但 12345 端口没人监听。
  → Tracking Streamer 没在推流。**IP 是对的，不用换。** 去头显里：
    1) 打开 Tracking Streamer 应用（不能只在后台）
    2) 点界面上的 **Start**
    3) 保持戴着 —— 摘下来会停止推流
```

真正不可达的地址仍然会退到「IP 不对」那条（验过 `192.168.99.99`，4 次全失败才下结论）。如果 ping 只通了部分，还会额外提示网络在掉线。

主程序的 `connect_streamer` 复用同一个函数，所以两边都修好了。
