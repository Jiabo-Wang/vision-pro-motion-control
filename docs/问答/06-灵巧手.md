## 1. 触觉：这只手没有

## 2. 手的力：能读，而且是活的

`FORCE_ACT`(1582)，6×int16，单位克，只读。驱动里已经封好了：[hand.py:197](vel_ar5/openvla-energy/VEL/src/hand_teleop/inspire_hand/hand.py#L197) 的 `get_force()`。

关键是**它有实测数据背书**——[migrate-hand-to-5070ti.md:71](vel_ar5/openvla-energy/VEL/docs/migrate-hand-to-5070ti.md#L71) 记着：食指张开时读回 `9~13`，顶住拇指时 `96~205`。会随受力变化，不是死值。这点要跟 `CURRENT`(1594) 区分开——那个在本固件上恒为 0，`VOLTAGE` 恒 -1，都是废的；`FORCE_ACT` 不是。

两个要注意的：

- **它是每个自由度的驱动器级夹持力估计，6 个标量**，不是接触点分布。别当触觉用。
- **现在没接进观测链路。** 在跑的 [inspire_hand_can.py:173](vel_ar5/openvla-energy/experiments/robot/ar5/drivers/inspire_hand_can.py#L173) 只调 `set_force()` 设保护阈值，从不读 `FORCE_ACT`。要用得自己接。接的时候注意：单帧往返 6~8ms，6 维要拆两帧，一次 `get_force()` 约 12~16ms —— 「手的 I/O 不能阻塞臂」那条老教训直接适用，不能在臂的 250ms 环里同步读。

## 3. 臂的力：接口有，但两个问题

AR5 是 7 轴、**关节力矩传感器标配**（[config.py:16-17](vel_ar5/openvla-energy/experiments/robot/ar5/config.py#L16-L17)）。`robot_class = "xMateErProRobot"` → 继承 `Cobot_7` → 有 `forceControl()` → `PyForceControl7`。两条读取路径：

- `robot.jointTorque(ec)` → 7 个关节力矩，不用进力控模式
- `fc.getEndTorque(FrameType.flange, ...)` → 关节测量力矩 / **外部**力矩 / 笛卡尔力(N) / 笛卡尔力矩(Nm)

**坑一：RT 实时流里没有力。** [RtSupportedFields.pyi](xCoreSDK-Python/Release/linux/arm/xCoreSDK_python/RtSupportedFields.pyi) 只有 `jointPos_m` / `tcpPose_m` / `elbow_m` / 外部轴，**一个 tau/torque 字段都没有**。1kHz RT 通道拿不到力，只能走非实时调用 —— 又是不能塞进控制环的东西。

**坑二：动力学模型现在是空的。** [config.py:150-152](vel_ar5/openvla-energy/experiments/robot/ar5/config.py#L150-L152) 的 `tcp_offset` / `payload_mass` / `payload_com` 全是 0，还挂着 `VERIFY` 注释。而「外部力」是控制器拿模型算出来的 —— 手大约 0.5kg 没填进去，手的自重会被整个算成外部受力，读数带系统性偏差。**用臂的力之前必须先把负载标定填了。**

## 型号拆开看

仓库记的 `RH56E@-OL-T2` 有两个转录笔误（`@`←`2`，`O`←`0`）。按厂商命名规则：

| 段 | 含义 |
|---|---|
| `RH56E2` | 机型 |
| `-0L` | **0 = CAN**（2=RS485），L = 左手 |
| `-T2` | **触觉传感器型号** |

`-T1` = 电阻式 **17 个**，量程 0–30N；**`-T2` = 电容式 5 个，量程 0–20N**，精度 ≤5%FS。

顺带一提，"0 = CAN"反过来印证了"这手走 CAN 不走 RS485"这个已实测的事实 —— 拆法是对的。

## 但有个硬问题：CAN 这条路带宽不够

现在的链路是 USB-CAN **纯透传**适配器、UART **115200**、CAN 数据段每帧 8 字节、实测单帧往返 6~8ms。

- 只读 5 个指尖 = 960 字节 → 120 帧 → **≈840ms，约 1.2 Hz**
- 读满 1062 点 = 2124 字节 → 266 帧 → **≈1.9 秒**

闭环里完全不能用。**正解是走网口** —— 厂商规格表写的通讯接口是「**Modbus TCP + CAN2.0**」，线缆有四路：航插 / **网口** / CAN-RS485 / 电源。触觉要用就接网线走 Modbus TCP，别想从 CAN 上捞。

## ❌ 触觉：走 CAN 拿不到

两条**独立**的硬理由，任何一条都足以否掉：

**一、地址空间根本不够。** CAN 扩展帧标识符里寄存器地址字段只有 **12 位**（bit14~25，上限 **4095**）—— 2024-12 版触觉手册里仍然这么写。触觉地址到 5123：

```
食指 指端/指尖/指腹  @4110 4128 4320  ── 超出 4095，无法寻址
拇指 指端/尖/中/腹   @4480 4498 4690 4708  ── 同上
掌心                 @4900            ── 同上
4128 实读 → ValueError: 寄存器地址 4128 超出 12 位 (0..4095)
```

**食指和拇指全都够不着，而这个项目正是食指+拇指捏取。** 好消息是驱动对超限地址是抛异常而不是静默截断，不会读错地址。

**二、3000 段读到的数据不可信。** 我做了对照实验，读手册里**根本没有寄存器**的地址：

```
@100   d0 07 ff ff ff ff ff ff   ★非零
@500   90 eb 01 00 ff ff ff ff   ★非零
@2000  90 eb 01 00 ff ff ff ff   ★非零   ← 和 @500 一模一样
@2990  ff ff ff ff ff ff ff ff   ★非零
```

**任意地址都返回非零数据**，500 和 2000 还返回完全相同的字节。所以"3000 段有数据"证明不了任何事。内容本身也对不上：手册规定每个触觉点是 int16、量程 0–4096，实测读到 38740 / 31864 / 65535。

顺带量了带宽：完整读一个 12×8 指尖块（192 字节 = 24 帧）**耗时 358ms，2.79 Hz** —— 就算地址够得着也没法闭环。

**结论：手有触觉硬件（`-T2` = 电容式 5 点），但 CAN 这条线拿不到它。**

## 机理


所以：

1. 第一次捏合 → 正常
2. **松手时臂还在动 → 目标突然断流 → latch**
3. 第二次捏合 → `step()` 照发，但每一帧都被 latch 拒掉 → **纹丝不动**
4. 而且屏幕上什么都不说

## 修法：摘离合后继续发零增量，直到臂真的停下来

```python
if engaged or settling:
```

| False（臂在动） | **151** | 持续发零增量 → 不会断流 → 不会 latch |

两个目标同时满足了：停着的时候不骚扰 IK，动着的时候不断流。

## 1. 握拳时拇指把食指顶开

是我自己写的耦合下限造成的，在 [inspire_hand6.py](Project_Atom/遥操/VR设备/inspire_hand6.py)。`index_floor(thumb_bend)` 是拇指弯曲量的函数：

| thumb_bend | 1000 | 800 | 600 | 500 | 400 | 0 |
|---|---|---|---|---|---|---|
| 食指下限 | 0 | 0 | 390 | 480 | 500 | **520** |

你握拳的顺序正好是最坏情况：先卷四指（食指到 0），**拇指后到**。拇指从 800 往下收的时候下限从 0 一路涨到 520，`clamp()` 就把已经卷好的食指从 0 推到 520 —— 就是你看到的「食指伸开」。

那组数是**捏合**姿态量的（拇指对着食指指尖），握拳时拇指压在卷好的四指外侧，根本碰不到指尖，这个约束在那里不成立。

改了两处：
- **单向规则**：下限只拦「食指正往拇指方向压下去」，绝不把已经在下面的食指往外推。碰撞是撞上去才发生的，离开拇指的方向永远放行。
- **默认关掉**耦合（`couple_index_thumb=False`）。真正的过载保护是力控阈值，手内部固件执行的；chf_ws 那套产线遥操也是各维独立钳位、没有任何交叉耦合。

6 项测试全过：握拳不再顶食指（开关都一样）、捏合仍拦在 480、捏住后张开放行、拇指让开后能全闭。

## 2. IK — chf_ws 给的启发很关键

它**根本不解方程**，而是当优化问题（CasADi+Pinocchio+IPOPT）：位姿误差是**代价**，关节限位是**约束**。所以它永远有解，够不到就交出够得到的里面最近的。

顺着这条线查，找到了真正的病根，和我原先想的不一样：

```
                    驱动接受率   丢:解不出   丢:被驱动拒
DLS（现在的默认）      13.9%        1          1291
```

**IK 几乎总能解出来，是驱动把解拒了。** [rokae_arm.py:787](vel_ar5/openvla-energy/experiments/robot/ar5/drivers/rokae_arm.py#L787) 有道 `joint_jump_max=0.15` 的闸，它自己的日志就写着「This is what an inverse-kinematics branch flip looks like」。7 轴冗余臂每帧独立求解会落到不同解支上，TCP 动几毫米、肘部甩几十度。被拒之后臂不动、目标继续跑，下一帧要跳得更远 —— **雪崩**，激进轨迹上接受率掉到 0.1%。

新的 [ar5_ik.py](Project_Atom/遥操/VR设备/ar5_ik.py) `AR5OptIK`（scipy L-BFGS-B，用 vel_ar5 现成的 fk/jacobian 写解析梯度，不需要 CasADi）：

| | 温和轨迹 | 激进轨迹 |
|---|---|---|
| DLS 接受率 | 13.9% | 0.1% |
| **AR5OptIK** | **100%** | **100%** |
| 跳变 p95 | 1.97° → **1.33°** | 16.22° → **3.03°** |
| ms 中位 | 1.3 → 2.9 | 1.5 → 2.9 |

三处没照抄 chf：
- **任务权重放大 10 倍**（50/0.5 → 500/5）。照抄的话手停住不动时姿态还差 **3.0°** —— 你本来就在说手腕姿态不对，再吃 3° 说不过去。放大后 0.29°。wT:wR 的 100:1 比例保留，那是「1cm 位置 ≙ 5.7° 姿态」的汇率，位置优先。
- **步长也做成 box 约束**（0.12 < 驱动的 0.15），这是 chf 没有的，正对上面那道闸。
- **正则按归一化行程算**，不是弧度 —— 弧度下 j0/j2/j4 天然比 j5/j6 重 12 倍，推的全是不该推的。

顺带两个实测结论：梯度是**精确**的不是近似（旋转误差 178° 时与数值差分差 3e-8，有个 `J_l⁻¹(φ)φ=φ` 的恒等式在起作用）；`w_reg` 从 0 加到 2.0，j5/j6 行程占用**纹丝不动都是 94%** —— 腕部姿态是任务完全决定的，不是冗余自由度，正则拉不回来，所以只留一点点防漂移。

跑法：`--ik opt`（默认）/ `dls` / `stock`。基准脚本存在 [bench_ik.py](Project_Atom/遥操/VR设备/bench_ik.py)。

两点要说清楚：基准的 DH 表是**合成的**（真表得从控制器 `getRobotCfg_DHparam` 读，臂没连），关节限位用的是真值，所以绝对数字别当实机指标，求解器之间的相对比较有效。mock 那轮跑通了 50Hz 臂 / 40Hz 手、姿态跟踪差 1° 以内，但 MockArm 没有 `_kinematics`，那轮验的是管路不是求解器 —— 求解器是单独按驱动的四道闸逐条验的。
